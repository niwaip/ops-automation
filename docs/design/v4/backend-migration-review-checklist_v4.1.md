> 本文配套 [Enterprise-Skill-Platform_Backend-Migration-Design_v4.1.md](file:///Users/chain/Documents/MyProject/ops-automation/docs/design/v4/Enterprise-Skill-Platform_Backend-Migration-Design_v4.1.md)、[backend-migration-first-batch-backlog_v4.1.md](file:///Users/chain/Documents/MyProject/ops-automation/docs/design/v4/backend-migration-first-batch-backlog_v4.1.md) 与 [backend-migration-pr-template_v4.1.md](file:///Users/chain/Documents/MyProject/ops-automation/docs/design/v4/backend-migration-pr-template_v4.1.md)，用于 reviewer、TL、架构 owner 在评审迁移 PR 时快速判断“这批改动是不是在正确推进迁移”。

---

## 1. 使用方式

本清单不用于检查“代码风格是否漂亮”，而是用于检查迁移 PR 是否满足以下三个核心要求：

1. 主问题单一。
2. 边界方向正确。
3. 验证与回滚充分。

建议在 review 时按以下顺序使用：

1. 先看 PR 描述是否说清主问题与边界。
2. 再看代码是否真的朝目标平面收敛。
3. 最后看验证记录和回滚点是否可信。

若前两步任一项不成立，后续 review 不建议继续深入到实现细节。

---

## 2. 一票否决项

出现以下任一情况，建议直接要求拆 PR 或退回重做：

1. 一个 PR 同时做“拆职责 + 迁目录 + 改协议 + 改部署”中的两项以上主问题。
2. 一边迁移，一边顺手修改外部 API、事件语义、数据库 Schema，但 PR 描述里没有单独说明。
3. 删除旧兼容壳、旧导出面或旧路径时，没有给出消费方切换完成的证据。
4. 只给出“服务启动成功”，没有行为级验证记录。
5. 涉及 Docker 挂载、Compose、服务路径迁移，却没有通过 `./docker/start-smart.sh` 做真实加载验证。
6. 新逻辑仍继续落进已冻结目录，例如 `core/platform`、`domain/*`、`@ops/contracts`。

## 3. Review 主清单

### 3.1 主问题检查

- 这个 PR 是否只解决一个主问题？
- PR 标题和描述是否能一句话说明本批次目标？
- 是否清楚列出了“纳入范围”和“不纳入范围”？
- 是否存在明显应该拆出去的第二主问题？

通过标准：

- reviewer 能在 1 分钟内说清这批 PR 的唯一主目标

### 3.2 边界方向检查

- 改动是否符合总设计中的目标归属？
- 新增逻辑是否进入目标子层，而不是继续堆回旧入口？
- 外部依赖是否开始收敛到稳定出口、façade 或兼容层？
- 是否避免让过渡层变成新的“大杂烩 façade”？

通过标准：

- 改完后，模块边界比改前更清晰，而不是仅仅换了目录

### 3.3 冻结规则检查

- 是否违反“冻结目录不再新增实现”的约束？
- 是否在 `domain/*` 中继续加入新的能力域逻辑？
- 是否在 `@ops/contracts` 中继续新增共享契约？
- 是否在 `core/platform` 兼容壳中继续堆真实业务实现？

通过标准：

- 旧路径只承担兼容、转发或收口职责，不继续扩张

### 3.4 兼容策略检查

- 是否保留了必要的兼容层、旧导出面或旧入口？
- 如果本批次新增了 façade，是否说明后续哪一批会继续收敛？
- 是否避免在同一 PR 同时“新增兼容层 + 删除旧壳 + 切全量调用方”？
- 回滚时能否只撤销本批次接线，而不影响其他链路？

通过标准：

- 兼容层是过渡工具，而不是新的长期主入口

### 3.5 工程影响检查

- 是否涉及 workspace、Compose、脚本、Docker 挂载、启动路径调整？
- 若涉及，是否把这类调整控制在单个服务或单条调用链范围内？
- 是否遵守通过 `./docker/start-smart.sh` 进行验证的规则？
- 是否有证据表明容器加载的是当前 worktree 代码？

通过标准：

- 工程改动范围可追踪，且验证记录可复现

### 3.6 验证记录检查

- 是否给出 typecheck 或等效构建结果？
- 是否给出与本批次直接相关的测试结果？
- 是否至少验证一个核心入口的真实行为？
- 若涉及容器 / 路径迁移，是否补了真实容器验证？

通过标准：

- 验证记录能支撑 reviewer 判断“这批改动确实生效”

### 3.7 回滚点检查

- 是否明确写出失败时回滚哪个 commit？
- 是否说明回滚后保留哪些兼容层或目录骨架？
- 是否避免“只能整体回滚多个不相关改动”的情况？

通过标准：

- 出现问题时可以只回退当前批次，不伤及其他迁移工作

## 4. 分阶段专项检查

### 4.1 Phase A 类 PR

重点看：

1. 是否真的在冻结入口，而不是借机夹带业务重构。
2. README、边界说明、目录归属是否一致。
3. 冻结规则是否足够明确，可被评审与执行引用。

### 4.2 Phase B 类 PR

重点看：

1. 是否只拆一个热点模块的一刀职责。
2. 是否优先补 façade / 子层边界，而不是直接大搬目录。
3. 超大文件是否开始变薄，而不是改名后继续膨胀。

### 4.3 Phase C 类 PR

重点看：

1. 目标平面是否真的开始承接真实实现。
2. 新契约包是否具备源码承载与构建能力。
3. 是否仍保留兼容入口，避免一次性切全部调用方。

### 4.4 Phase D 类 PR

重点看：

1. 是否只迁一个真实运行单元。
2. Compose、workspace、脚本变更是否与该服务迁移绑定。
3. 是否做了真实容器加载验证和行为级验证。

### 4.5 Phase E 类 PR

重点看：

1. 删除动作是否晚于消费方完成切换。
2. 是否保留明确回滚点。
3. 是否把清理和新需求开发混在同一个 PR。

## 5. 首批 PR 快速检查表

### 5.1 `PR-01` 基线冻结与归属说明

- 是否清楚标出冻结目录和目标平面？
- 是否补齐了关键 README 或边界说明？
- 是否没有夹带业务实现改动？

### 5.2 `PR-02` `capability-release` 首刀拆分

- 是否只处理 `capability-release` 的内部职责收敛？
- 是否保持 controller、route、外部入口稳定？
- 是否让 `release / compiler / validator / publisher / audit` 边界更清晰？

### 5.3 `PR-03` `temporal-workflow` runtime-bridge 首刀

- 是否真的把运行时执行辅助从设计时主层切开？
- `activity/` 是否回到设计时定义管理语义？
- 是否避免同步处理 browser 辅助和 `execution-flow`？

### 5.4 `PR-04` `browser/*` 依赖方向冻结

- 是否真正收紧了 `planner/*` 对浏览器内部实现的深层依赖？
- 是否开始通过稳定出口暴露浏览器域依赖？
- 是否没有顺手动 gateway、WebSocket、模板域迁移？

### 5.5 `PR-05` `backend-contracts/*` 首个源码化子包

- 是否至少有一个子包具备 `src/`、`tsconfig`、构建脚本和统一导出？
- 是否只切了一条最短消费链？
- 是否保留 `@ops/contracts` 兼容壳，没有提前删旧包？

## 7. 一句话结论

迁移 PR 的评审重点不是“代码有没有改动”，而是“这批改动是否让边界更清晰、风险更可控、回滚更简单”。只要这三点说不清，就不应把它当成合格的迁移批次。
