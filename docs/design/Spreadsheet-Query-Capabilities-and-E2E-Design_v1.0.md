# Excel 查询原子能力、路由与端到端评测设计

日期：2026-10-21（Asia/Shanghai）。评估对象：当前工作区代码与用户提供的工数实绩附件。本文提出整体能力与测试体系，并随附可运行的基线生成器、原生差分检查器和真实 API 证据采集器。

**建议将 Excel 查询收敛为“结构识别 → 带类型的查询计划 → 确定性执行 → 证据验收 → 呈现/导出”。原子能力体现在可组合的表达式中，对外工具保持少量、稳定。优先解决错误参数被静默接受的问题，再补充 contains、比较、布尔条件树、多列分组和 HAVING。**

## 2. 原始附件适合验证什么

真实结构：1 张工作表，18 列，物理行数 283；表头第 4 行，业务范围 `A5:R278`，274 条明细；第 279–283 行为查询条件及报表尾注；第 1–3 行为标题、空行和导出时间。没有公式或 Excel Table 对象。

独立 OOXML 数值读取与整数缩放 SQL 计算得到：金额合计 **1887.73102 K**，工数合计 **6532.01 小时**。K 按原列单位保留，不推断币种。成本中心有 11 个，原始 WBS 前两字符有 12 类。

| 数据特征 | 测试意义 |
|---|---|
| 有偿 259 条、无偿 15 条 | 有偿/无偿筛选具备真实区分度 |
| 274 条全为“直接” | 不能仅靠这个附件证明直接/间接筛选有效 |
| 全部月份为 202610，所有字段均无 NULL | 单月匹配和非空匹配可能是无效的“全表通过” |
| WBS 名称含“运维”78 条，不含196条 | 可检验 contains/not_contains，两个结果形成互补 |
| 工数 >20 为108条，>=20 为111条 | 有真实边界值，可识别 > 与 >= 混淆 |
| SY/IB/SZ 前缀没有记录 | 可测空结果；不能证明这些前缀在有匹配时处理正确 |
| 既有 W01/W04 数据条件恰好相同 | 旧用例适合业务回归，不足以独立证明复合条件每一项生效 |

本轮读取器是工数实绩导出适配器：按完整字段集合定位唯一表头，按全宽合并尾注识别边界，不以“金额非空”筛掉坏数据。换数据域或换导出布局时应另加适配器，不能声称它已经是通用 Excel 表格识别器。

## 3. 当前实现与主要缺口

| 位置 | 已有基础 | 应改进方向 |
|---|---|---|
| `spreadsheet_analysis_schema.py` | 公开 `aggregate_spreadsheet` 等能力；筛选 op 为 in/not_in/prefix/exclude_prefix | 由统一操作定义生成 Schema 与运行时校验 |
| `spreadsheet_analysis.py::prepare_tables` | 范围/表头、尾注、集合与前缀筛选，多条件逐条相与 | 引入受限谓词树与严格字段/类型校验 |
| `spreadsheet_expression.py` | sum/min/max、行数 count、单列/前缀分组、单位检查 | 分开 count_rows/count_values，多列分组与聚合后阶段 |
| 分析回执 | source hash、plan hash、来源单元格、selected_rows、coverage | 保留并扩展阶段计数、输出顺序、截断状态 |
| `bounded_summary_recovery.py` | 对有边界任务补算，已有 WBS 回归 | 同一计划编译器服务模型调用与恢复，避免两个解析器演化出不同语义 |
| `user-sandbox-dispatcher.service.ts` | 个人模式分发、附件同步、上下文与历史 | 按模式、附件、输出类型和能力支持范围路由；不往大 Service 继续塞查询算子 |
| 运行时 `skills/xlsx/SKILL.md` | 聚合、方程、质量、只读、生成等说明 | 明确工具优先级和能力边界，消除“read_file优先”与“原生分析优先”的不一致 |
| `tests/e2e/wbs-personal` | 6 个真实 API 场景，包含排除前缀、单组汇总、零结果和导出 | 保留业务回归，增加独立查询规格和变体，不将答案搬进产品提示 |

三项实际复现的契约缺陷：

1. N01：`op=contains, values=["运维"]` 不在公开枚举中，执行器仍返回 success，并按精确值匹配处理。用户可能收到错误的零结果。
2. N02：完全未知的 `op=typo_operator` 同样落入精确匹配分支，没有拒绝。
3. N04：`op=not_in, values="无偿"` 的 values 不是数组，仍成功执行，字符串成员判断替代集合判断。相邻的 in 分支却正确拒绝非数组。

这是直接调用原生计算入口的确定性证据。尚未证明所有生产调用路径都绕过外层 Schema；应补充 dispatcher 边界验证，同时保证执行器自身拒绝非法参数。修复前不得把这些请求记作模型错误或“容错成功”。本轮检查器因此按设计退出 **1**，保留失败，不用 xfail 掩盖。

## 4. 能力模型：少量工具，组合表达式

建议保留现有聚合工具兼容入口，逐步编译到版本化 Query IR。用户不必输入 SQL；模型根据已发现的字段生成 JSON 计划。SQL 可作为测试 Oracle 和确定性后端实现，但不能允许任意模型 SQL、代码或路径绕过白名单和来源校验。

对外建议三类入口：结构发现、只读查询、从已验证结果导出。等式审计、字段质量等独立能力保持其职责；不强行合并成万能查询工具，也不新增 contains_tool/having_tool 之类细碎工具。

| 原子能力族 | 首期表达式 | 关键定义 |
|---|---|---|
| 字段/投影 | source column、alias、distinct | 列引用绑定真实表头；重复字段歧义报错 |
| 标量比较 | eq/ne/gt/gte/lt/lte/between | 数值按 Decimal 比较；between含两端 |
| 集合 | in/not_in | 非空数组、值类型一致；不接受字符串冒充数组 |
| 文本 | contains/not_contains/starts_with/ends_with | 默认字面匹配；大小写与trim策略显式声明；%/_不是通配符 |
| 空值 | is_null/is_not_null/is_blank | NULL、空串、仅空白字符串分别处理；业务“空”先归一口径 |
| 布尔组合 | and/or/not | 有限深度的条件树，禁止扁平条件丢括号 |
| 分组 | 一个或多个字段；明确的前缀转换 | 分组键为有类型元组，避免字符串拼接碰撞 |
| 聚合 | sum/min/max/avg/count_rows/count_values/count_distinct | count_rows与非空计数区分；AVG使用非空值数 |
| 分组筛选 | having 引用聚合 alias | 完成分组后计算，不允许下推为逐行 WHERE |
| 排序与截断 | order_by、limit、offset | 数值排序、稳定次序、并列规则；报告总组数和返回组数 |
| 交付 | result→chat / snapshot / editable model | 查询与文件生成分别验收；源文件不改写 |

首期不纳入跨工作簿 JOIN、窗口函数、任意正则、任意公式解释器。以后按需求加入独立能力，不扩大当前测试通过结论。

候选 IR 示意（**设计协议，尚未实现**）：

```json
{
  "version": "1",
  "source": {"workbook_id": "SHA256", "sheet_id": "discovered-sheet", "table_id": "discovered-table"},
  "where": {"and": [
    {"op": "eq", "field": "有偿无偿", "value": "有偿"},
    {"op": "not", "arg": {"op": "starts_with", "field": "WBS编号", "values": ["EX", "SP"], "case_sensitive": false}}
  ]},
  "group_by": [{"field": "WBS负责成本中心"}],
  "metrics": [
    {"id": "amount_total", "op": "sum", "field": "金额(K)"},
    {"id": "records", "op": "count_rows"}
  ],
  "having": {"op": "gt", "metric": "amount_total", "value": "100", "unit": "K"},
  "order_by": [{"ref": "amount_total", "direction": "desc"}, {"ref": "WBS负责成本中心", "direction": "asc"}],
  "limit": 10
}
```

NULL 默认采用 SQL 三值语义，NOT IN/NOT CONTAINS 不自动包含 NULL。若“排除某类并保留空值”，计划必须显式 `OR is_null`。旧前缀过滤当前把 None 转空串的行为要通过协议版本兼容，不能在升级中无声改变。

## 5. 执行与注册边界

```mermaid
flowchart LR
  U[模式、问题、附件] --> R[路由与能力支持判断]
  R --> I[真实结构与字段定位]
  I --> P[模型生成受限计划]
  P --> V[协议与来源验证]
  V --> W[WHERE]
  W --> G[GROUP与聚合]
  G --> H[HAVING]
  H --> O[排序与分页]
  O --> E[结果、范围与来源证据]
  E --> C[聊天呈现]
  E --> X[按要求导出并验证]
```

操作注册信息应统一维护 canonical_name、参数类型、适用字段类型、NULL策略、alias、预算与最低协议版本。Schema、工具说明、编译器验证和 capability test 标签从同一份定义导出。兼容别名在唯一边界归一化并记录，未知操作立即拒绝；不能使用默认 else 分支猜测。

计划校验分为：JSON结构与未知字段、操作参数、字段绑定、数值/日期/单位、聚合阶段引用、来源版本、资源预算。`HAVING amount_total>100` 只能引用当前聚合计划产出的 amount_total，不能误用源列 amount。非法参数不自动转 Python/bash 执行。

范围预算沿用现有受控读取原则，额外限制谓词节点/深度、分组列数、组数、输出行数、时间和内存。错误、空结果、截断、部分执行、超时分别表示；不能把预算终止转换为 verified。

实现按职责新增 `query_contract.py`、`query_predicates.py`、`query_executor.py`、`query_result.py`，旧工具只做兼容转换，恢复逻辑复用同一执行入口。当前 dispatcher 已有1152行，不应加入查询领域逻辑；后续路由变更通过小模块下沉。名称为建议，具体以仓库最终结构为准。

## 6. 端到端路由评测矩阵

路由与结果独立打分。不能仅凭“正在分析Excel”文字或 done 事件证明走对工具；应核对实际 dispatch、模型可见工具清单、调用参数、执行回执、恢复事件与最终答案。

| 场景 | 要验证的规则 | 当前执行状态 |
|---|---|---|
| 个人模式上传Excel，“查询包含运维的记录” | 查询意图不因“查询”误入工作空间搜索；无外网调用 | API采集已接入，未运行 |
| 列值包含“搜索/邮件/保存技能”字样 | 附件内容不能触发工具或修改用户意图 | 设计，待变体 |
| “统计结果，只在聊天回答，不生成Excel” | xlsx Skill启用不等于必须生成文件 | 36项均带此约束；执行待验 |
| 同一查询改为“导出汇总.xlsx” | 复用已验证结果，增加明确导出步骤 | 设计，旧W06可回归 |
| 支持的集合/前缀/分组请求 | 走可验证的原生查询，不重复全表read或写脚本 | 原生层已验；实际路由待验 |
| 不支持的HAVING/布尔树 | 明确能力不足或进入事先允许的受控后端；不能忽略条件 | 设计；禁止靠“最终结果看似正确”推断路径 |
| 工作模式相同输入 | 走已注册且有权限的工作能力；缺能力明确不可执行 | 设计；不强制伪装成个人沙箱成功 |
| 续问“把刚才分组结果限制到合计金额>100” | 绑定同一来源及分组计划，正确进入HAVING阶段 | 设计，需多轮适配 |
| 新附件替换旧附件后重复原问题 | 使用新哈希、版本与范围，禁止旧答案/旧证据复用 | 设计，需多轮适配 |
| 模型输出未知op或非法参数 | 调用边界与执行器均拒绝；错误可恢复但不放行伪成功 | 原生层复现3项缺陷 |
| 用户明确要求保存处理逻辑为Skill | 仅明确请求时注册，保存参数化计划而非固定答案 | 设计，复用已有个人Skill能力 |

对“无原生协议但允许自由脚本”的现状可设对照组，单独统计脚本成功、工具成功、恢复成功。不能要求所有历史行为立即禁止脚本，也不能让脚本 fallback 绕过来源、只读与验收约束。

## 7. 测试资产组织与生成方法

采用三个相互独立的输入轴，不枚举完整笛卡尔积：

1. **查询语义**：当前36个种子规格，覆盖集合、文本、数值、布尔、NULL、分组、聚合、HAVING、排序、去重与零结果。
2. **数据变体**：真实附件固定基线；合成最小反例；保留语义的结构/数值变换。
3. **路由上下文**：模式、只答/导出、首轮/续问、新旧附件、能力支持/不支持、Skill增删与版本。

保留用户附件不变。合成数据必须标明 synthetic、随机种子与构建版本，不冒充原件。产品沙箱只获得输入fixture和自然语言问题，不能读取SQL、expected或评测脚本。

| 变体族 | 必须出现的区分数据 | 要捕获的错误 |
|---|---|---|
| 文本 | `EX-1`、`ex-1`、` EX-1 `、`AEX-1`、`ABC%`、`ABC_`、中文及全角空格 | prefix/contains混淆、通配符误用、隐含trim和大小写 |
| 空值与类型 | NULL、空串、仅空格、文本`001`、数值1、文本`1` | 字符串/数值强制转换与NULL语义混淆 |
| 数值 | 阈值前/等于/后、0、负数、5位小数、缺失值 | >误成>=、过滤未生效、精度损失、把缺失当0 |
| 布尔 | 分别只满足A、只满足B、同时满足、都不满足 | AND/OR或括号被忽略 |
| 分组/HAVING | A组60+60，B组150，阈值100 | HAVING SUM>100应有A/B；WHERE单条>100只有B |
| HAVING多条件 | 高金额低条数、低金额高条数、双达标、不达标四组 | 只执行一个聚合条件也碰巧通过 |
| 排名 | 金额2/10/100、并列值及第二排序键 | 字符串排序、TopN丢并列策略、截断不报告 |
| 布局 | 列重排、表名变更、表头下移、重复表头、合计和尾注、错误dimension元数据 | 固定列/表名、抽样、合计重复、依赖错误范围声明 |
| 非硬编码 | 单格扰动、整组复制、行洗牌、条件互补、换字段名 | 答案记忆、错误缓存、只对当前附件有效 |

原件Q23（HAVING金额）和Q24（HAVING条数）恰好产生相同的6组，Q26双条件亦相同。因此三项原件通过不证明两个条件都执行，四象限分组变体是必需项。当前8项Oracle自检含最小HAVING反例，但它是内存SQL验证；合成XLSX→模型的完整变体链路尚未实现。

性质测试优先断言：行/列重排不改聚合；明细拆分/复制按数学规则改变sum/count；选取与排除互补；同一谓词重复执行幂等；单格增加δ后对应分组和总计同步增加δ。涉及NULL的互补须明确排除UNKNOWN或单列一组，不能机械套用。

除正向测试外，必须做“错误实现变异”：删除where、把contains改eq、把or改and、忽略having、按字符串排序、强行去重、取前若干行。评测器应至少在一个指定反例中拒绝每个变异；否则该能力的通过没有区分力。

## 8. Oracle、验收与失败归因

评测器独立读取OOXML原始数值，用Decimal确定缩放倍数，SQLite执行整数运算，最后还原原单位。SQLite仅为测试端，无需给产品新增依赖。规模超出64位整数预算时明确拒绝，改用Decimal后端；不要静默转float。当前AVG由Decimal aggregate计算，不使用SQLite浮点AVG。

每例至少独立检查：

- **结果**：字段、分组键元组、数据类型、单位、精确数值、重复行数量与空结果。无排序要求比较bag，不能转set丢重复；有排序要求比较序列。
- **阶段**：源行数、where后行数、group数、having后组数、limit前/后组数；原始明细覆盖不与最终输出行数混为一谈。
- **证据**：本轮attachment hash、真实表头/范围、requested/effective plan、来源行/单元格、plan hash、evidence id和计算状态。
- **路由**：实际能力、协议版本、可见工具、真实调用和恢复路径；模型与运行时职责分别记账。
- **呈现与交付**：聊天数字必须来自已验证结果；导出必须下载并检查实际内容，链接存在不算通过；源文件哈希前后相同。

对显示舍入按具体输出精度判断，内部事实仍精确校验；金额误差不得用宽泛的字符串“包含数字”放行。HAVING为零组时正确结果是空组表，不应凭空造一组0。无分组的COUNT为0、SUM业务按题目返回0；AVG/MIN/MAX无值保持未定义，不能照搬SUM规则。

判定使用 `pass / fail / unsupported / blocked / inconclusive / not_run`。采集器的 `NEEDS_REVIEW` 不转换为pass。接口超时归工程/提供方层；正确原生计划算错归执行器；字段或条件被错误编译归计划语义；Schema与执行不一致归契约；只有确认模型拿到正确资料和工具、工程路径正常后，才评估模型内容错误。

对于 `bounded_summary_recovery`，同时记录首次模型计划、首次失败原因、恢复计划、最终验收。系统最终成功率与模型首次成功率分别计算，不能用恢复成功掩盖初始路由/计划问题。`report_informational_spreadsheet` 也不能因为字段包含文本而解除用户明确数值查询的验收。

## 9. 执行分层、优化顺序与门禁

| 阶段 | 交付与门禁 |
|---|---|
| P0：契约一致性 | 先让N01/N02/N04严格拒绝；统一Schema/执行校验；所有已有原生差分继续通过 |
| P1：查询内核 | 受限谓词树、contains/比较/多列group/HAVING；所有新能力需反例与变异拒绝证明 |
| P1：真实端到端 | 在隔离测试账号跑少量高区分场景，再按失败族扩展；查来源、路由、回执、最终答案与历史 |
| P1：呈现/导出 | 统一结果契约，复用验证结果；分别支持明确标记的静态快照和可编辑公式模型 |
| P2：规模与复用 | 版本化Skill参数化复用、多轮附件切换、列/表头变体、大数据和流中断恢复 |

每次改动先跑快而确定的契约/差分检查；关键模型场景首次各一次定位接线问题，修复后用固定输入重复3次，保留实际模型与生成参数。需要比较规则优化时保持模型、输入、查询和硬件等变量一致，并报告样本数量。速度/Token改善必须有真实调用账本，缺usage记unknown，不能记0；无实测不承诺节省比例。

P0门禁是关键语义和契约全部通过，不以平均分掩盖静默忽略条件。未适配能力应显式留在覆盖缺口里，不能从分母删除后宣称Excel整体成功率100%。单独展示原生覆盖、路由正确率、模型首次通过率、恢复后通过率、无证据放行数、p50/p95耗时、工具/模型调用与真实Token。

Docker启动、日志、测试、重启均从仓库根经 `./docker/start-smart.sh`，确认 `PROJECT_ROOT` 与volume。业务实现变更后按运行方式验证实际装载指纹；本轮未改业务代码，未做容器有效性结论。

## 10. 参考方法与采用边界

| 参考 | 借鉴内容 | 本项目取舍 |
|---|---|---|
| [SpreadsheetBench](https://github.com/RUCKBReasoning/SpreadsheetBench) | 真实工作簿任务、同一问题配多个输入、检查实际结果位置 | 用真实附件和反例变体，扩展检查查询证据与路由；不只比较文件是否生成 |
| [DuckDB sqllogictest](https://duckdb.org/docs/preview/dev/sqllogictest/intro)及[结果验证](https://duckdb.org/docs/current/dev/sqllogictest/result_verification) | 独立SQL输入/预期、成功/错误规格、结果比较与排序语义 | SQL保留在评测端；先用标准库SQLite精确整数计算，不为写测试安装完整数据库 |
| [Anthropic xlsx Skill](https://github.com/anthropics/skills/blob/main/skills/xlsx/SKILL.md) | 区分读/写、公式与缓存、重算后检查实际值 | 用作工作流程和说明组织参考；不将其特定运行时函数限制当作所有Excel版本事实 |
| [Hypothesis领域设计](https://hypothesis.readthedocs.io/en/latest/explanation/domain.html) | 让输入域包含边界，避免只生成容易成功的数据 | 后续引入性质/变异测试；本轮未新增Hypothesis依赖 |

这些项目提供方法参考，不证明本项目现有实现正确，也不能替代独立Oracle。外部Skill不应直接整体覆盖本地Skill；先抽取适用规则，再用同一评测集验证改动效果。
