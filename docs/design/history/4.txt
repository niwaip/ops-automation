## 一、这个仓库到底做了什么？（一句话）

**`chrome-novnc-docker` = 把「有头 Chrome（GUI）」跑在 Docker 里，并通过 noVNC 在浏览器中远程访问，同时暴露 CDP 端口供自动化使用。**

官方描述非常直接：

> *“A complete Docker solution for running Google Chrome with virtual display (Xvfb) and noVNC web interface on Ubuntu Server (headless).”* [\[github.com\]](https://github.com/johnymoo/chrome-novnc-docker)

也就是说，它把你前面反复讨论的这条链路**完整打包好了**：

    Chrome (headed)
      └─ Xvfb (虚拟显示)
           └─ x11vnc
                 └─ noVNC (Web)

并且**额外做了一件关键的事**（对你非常重要）：

✅ **开放 Chrome DevTools Protocol（9222）**  
→ Agent / Playwright / Selenium 可以连接  
→ 人和 AI 操作的是 **同一个浏览器实例**

***

## 二、目录结构（理解它怎么工作的关键）

仓库结构（精简）如下： [\[github.com\]](https://github.com/johnymoo/chrome-novnc-docker)

    chrome-novnc-docker/
    ├─ Dockerfile
    ├─ docker-compose.yml
    ├─ scripts/
    │  ├─ start.sh
    │  ├─ start-xvfb.sh
    │  ├─ start-chrome.sh
    │  ├─ start-novnc.sh
    ├─ docs/
    ├─ examples/
    └─ README.md

### 核心思想很清晰：

*   **Dockerfile**：只负责安装依赖（Chrome / Xvfb / noVNC / supervisord）
*   **scripts/**：每个组件一个启动脚本
    *   Xvfb
    *   Chrome
    *   noVNC
*   **入口脚本统一编排**
*   **docker-compose** 做端口暴露与参数管理

这是一个\*\*工程化程度明显高于“教程级 Dockerfile”\*\*的实现。

## 三、最重要的：怎么用？（官方推荐两种方式）

### ✅ 方式一：Docker Compose（官方推荐）

这是 README 里**首推的方式**。 [\[github.com\]](https://github.com/johnymoo/chrome-novnc-docker)

#### 1️⃣ 克隆仓库

```bash
git clone https://github.com/johnymoo/chrome-novnc-docker.git
cd chrome-novnc-docker
```

#### 2️⃣ 启动容器

```bash
docker-compose up -d
```

#### 3️⃣ 访问 noVNC（浏览器接管）

    http://localhost:8080/vnc.html

打开后点击 **Connect**，你就能看到容器里的 **真实 Chrome GUI**。 [\[github.com\]](https://github.com/johnymoo/chrome-novnc-docker)

> ✅ 这一步正好对应你说的：  
> “出意外 → 人接手 → 直接操作浏览器”

***

### ✅ 方式二：直接 `docker run`

如果你不想用 compose，也可以直接跑（README 给了示例）。 [\[github.com\]](https://github.com/johnymoo/chrome-novnc-docker)

```bash
docker run -d \
  --name chrome-novnc \
  -p 8080:8080 \
  -p 5900:5900 \
  -p 9222:9222 \
  ghcr.io/yourusername/chrome-novnc:latest
```

#### 端口含义（非常关键）

| 端口       | 用途                                  |
| -------- | ----------------------------------- |
| 8080     | noVNC Web 访问                        |
| 5900     | 原生 VNC（可选）                          |
| **9222** | **Chrome DevTools Protocol（自动化入口）** |

## 四、三种典型使用场景（README 给的）

### 1️⃣ 人工接管（noVNC）

*   打开浏览器
*   访问：

<!---->

    http://<host>:8080/vnc.html

*   点击 Connect

✅ 适合：

*   登录
*   验证码
*   手工纠偏

***

### 2️⃣ Playwright 自动化（同一浏览器）

README 里直接给了例子（这是**关键价值所在**）： [\[github.com\]](https://github.com/johnymoo/chrome-novnc-docker)

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.connect_over_cdp("http://your-server-ip:9222")
    context = browser.new_context()
    page = context.new_page()

    page.goto("https://example.com")
    page.screenshot(path="screenshot.png")

    context.close()
    browser.close()
```

⚠️ **重点不是 Playwright 本身**，而是：

> ✅ **Playwright 连接的是这个“有头 Chrome”**
> ✅ 和 noVNC 看到的是 **同一个 session / profile**

这正是你前面说的：

> “AI 在跑 → 出错 → 人接手 → 再交还给 AI”

***

### 3️⃣ Selenium（同理）

README 也列了 Selenium 方式，原理完全一致： [\[github.com\]](https://github.com/johnymoo/chrome-novnc-docker)

*   Chrome 由容器托管
*   Automation 通过 9222 连接

## 六、你下一步可以怎么“进阶使用”它（建议）

基于这个仓库，你可以很自然地做三层增强（**不用改核心结构**）：

### 1️⃣ 接管权限控制（你最关心）

*   noVNC 前面加：
    *   API Gateway
    *   一次性 token
    *   Session state（只读 / 可操作 / 冻结 agent）

✅ **noVNC 本身不管权限，但这个设计正好方便你插手**

***

### 2️⃣ 模板化执行（你前面提的核心目标）

*   Agent 通过 CDP 执行「模板化 action」
*   noVNC 只在异常状态打开
*   Playwright trace + 人工接管日志合并

这个仓库**已经满足底层前提条件**。

***

### 3️⃣ 多 Session / 多容器

*   一容器 = 一浏览器 session
*   用 orchestrator（K8s / Nomad / ECS）拉起
*   noVNC URL 和 CDP URL 都是 session scoped
