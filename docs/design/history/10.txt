# 1) 需求确认结论（Freeze Summary）

# 2) 要件定义（SRS v0.1）

下面是把你的答案“写成可实现要件”的形式。

## 2.1 角色（Actors）

1.  **Employee（员工）**：创建会话、观看/接管、点击继续
2.  **Admin（管理员）**：配置用户/权限/Policy、维护模板仓库、查看审计
3.  **Replay Engine（回放引擎 / Agent 身份）**：执行模板、产生 step log、响应冻结/恢复
4.  **Session Broker（会话经纪人）**：分配 worker、挂载 profile、维持锁与租约、关闭会话写回

***

## 2.2 核心系统组件（Logical Components）

### Control Plane（控制平面）

*   AuthN：账号密码（后续可换 SSO）
*   AuthZ：RBAC/Policy（管理员配置）
*   Profile Registry：profile 元数据（owner、版本、策略标签）
*   Profile Lock Service：写锁 `user_id -> session_id`
*   Session Broker：创建会话、调度 worker、签发 noVNC/CDP 访问令牌（即使初期不做 token，也要保留接口）
*   Audit/Log：step log 汇聚与存储

### Execution Plane（执行平面）

*   **Replay Engine**（外置服务）：解析 DSL、执行步骤、断言/等待/重试、幂等
*   通过 **CDP 连接到浏览器会话**（9222 或经代理），并能够被控制面冻结/恢复输入

> Playwright Trace Viewer 是成熟的 trace 载体（后续如升级审计深度可直接对接）。 [\[github.com\]](https://github.com/ConSol/docker-headless-vnc-container), [\[wpon.cn\]](https://www.wpon.cn/35436.html)

### Runtime Plane（运行时平面）

*   Browser Worker：基于 `johnymoo/chrome-novnc-docker`（headed Chrome + Xvfb + noVNC + CDP） [\[github.com\]](https://github.com/skyvern-ai/skyvern)
*   Profile PVC/NFS：挂载到 worker（Chrome user-data-dir 指向挂载路径）
*   noVNC：供人工接管（8080）
*   CDP：供自动化（9222） [\[github.com\]](https://github.com/skyvern-ai/skyvern)

***

## 2.3 功能要件（Functional Requirements）

### FR-1 会话创建（Create Session）

*   员工可发起“新会话”（一任务一会话）
*   会话创建时可选择“加载我的 profile”（默认加载）
*   控制平面必须：
    1.  校验员工权限
    2.  申请写锁（若已有 RW 锁 → **直接拒绝**）
    3.  分配 Browser Worker（Pod）
    4.  挂载员工 profile PVC/NFS（RW）
    5.  启动 Chrome 指向该 profile
    6.  返回接管入口（noVNC URL）与执行入口（供引擎连接的 CDP endpoint）

> `chrome-novnc-docker` 的端口契约（noVNC/VNC/CDP）是这一流程对齐的基础。 [\[github.com\]](https://github.com/skyvern-ai/skyvern)

### FR-2 模板回放（Run Template）

*   Replay Engine 读取模板（template\_id + params）
*   以语义定位为主执行：role/label/text
*   每一步必须产出 step log（成功/失败、用到的定位策略、耗时、错误信息）
*   遇到异常按分级处理（至少包含：可自动重试 / 需要人工接管 / 必须终止）

### FR-3 人工接管（Takeover）

*   当进入“需要人工接管”状态：
    *   控制平面将会话状态标记为 **HUMAN\_CONTROL**
    *   Replay Engine 必须冻结所有输入（不再派发 CDP Input 事件） [\[deepwiki.com\]](https://deepwiki.com/jlesage/docker-baseimage-gui/2.4-novnc-web-client), [\[microsofte...rosoft.com\]](https://microsoftedge.microsoft.com/addons/detail/ajdpfmkffanmkhejnopjppegokpogffp)
    *   noVNC 通道允许员工接管浏览器交互（实时画面+操作）

### FR-4 人工点击继续（Resume）

*   员工在 Portal 点击“继续”
*   控制平面将状态切回 **AGENT\_RUNNING**
*   Replay Engine 恢复输入并从指定 step 继续（需要一次 state sync：URL/关键元素判断）

### FR-5 会话关闭与写回（Close Session + Write-back）

*   会话关闭时必须：
    *   释放写锁
    *   将 profile 写回（因为 PVC/NFS RW 挂载，实质是“确认关闭”+“记录版本/元数据”）
    *   记录审计（至少：谁关闭、何时关闭、模板执行结果、是否发生接管）

***

## 2.4 非功能要件（Non-Functional Requirements）

### NFR-1 隔离与安全边界

*   浏览器会话容器不承载权限决策逻辑；权限由控制面裁决（防止执行体自我绕过）
*   控制面必须能区分员工与引擎身份（不同 credential / 不同权限集）

### NFR-2 并发与一致性

*   profile 写锁为强约束：同一 user\_id 同时仅 1 个 RW session
*   第二个创建请求直接拒绝（返回明确错误码与提示）

### NFR-3 可观测性

*   Step-level log 是必需品
*   （可选增强）后续可引入 trace 作为证据链（Playwright trace viewer） [\[github.com\]](https://github.com/ConSol/docker-headless-vnc-container), [\[wpon.cn\]](https://www.wpon.cn/35436.html)

### NFR-4 可部署性

*   Kubernetes 部署，PVC/NFS 作为 profile 持久化介质
