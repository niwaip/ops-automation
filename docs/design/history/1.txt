太赞了——你描述的其实是一个\*\*“LLM 只做编译（template 化），执行引擎做确定性回放（replay），异常时人类可接管（human takeover）”\*\*的三层架构。这正是把 **token 成本、成功率、幂等性、可审计性**同时做到位的路线。

下面我给你一个**可落地的端到端方案**：从模板（DSL）怎么设计、怎么让 AI 更少 token 生成、更高成功率，到执行引擎如何做幂等、如何检测“意外”、以及如何无缝接管（保持同一个浏览器会话）。

***

## 0) 目标拆解（你要的 4 个关键词如何落地）

1.  **模板化**：LLM 输出的是“动作模板”（可参数化、可复用），不是每次都从零写步骤。
2.  **减少 token**：模板是短的；运行时只传参数、上下文摘要和少量状态。
3.  **提高成功率**：执行层用可预测的规则（稳定定位、重试、验证、回滚/补偿）替代 LLM 的“猜”。
4.  **幂等 + 可接管**：每一步都有 precondition/postcondition；异常时把同一 session 的控制权交给人（实时可视+可交互）。

***

# 1) 推荐总体架构（Planner/Compiler → Replay Engine → Human Takeover）

### 1.1 三层分工（强烈建议）

**A. Template Compiler（AI / LLM）**

*   输入：业务意图 + 页面“语义快照”（不是整页 HTML）+ 你已有模板库
*   输出：**模板（DSL）+ 参数 schema + 校验规则**
*   不直接跑浏览器（或者只在“录制模式”里跑一次）

**B. Replay Engine（确定性执行引擎）**

*   输入：模板 + 参数 + 运行时状态
*   输出：执行结果、日志、截图/trace、步骤级状态
*   负责：定位、等待、重试、断言、幂等、防重复提交

**C. Takeover UI（人类接管）**

*   用 WebRTC/noVNC/Guacamole 之类方式**接入同一浏览器 session**
*   人能看、能点、能输入
*   接管后动作也被记录回模板/补丁（可选）

***

# 2) 核心：模板（DSL）怎么设计，才能“少 token + 高成功率 + 幂等”

你不要让 LLM 输出 Playwright 代码（太长、不可控），而是输出一个**短 DSL**，执行引擎负责解释。

## 2.1 模板 DSL 需要具备的能力清单

### ✅ 1) 语义定位（Semantic Locator）

避免 selector 易碎，优先用：

*   accessibility role/name（按钮、输入框、菜单项）
*   可见文本（含同义词匹配）
*   label/placeholder/aria-label
*   相对关系（“在 X 右侧的输入框”）
*   稳定属性（data-testid、name、id —— 如果你能推动业务系统加 data-testid，成功率会跃迁）

### ✅ 2) Step 级别的 pre/post condition（幂等基础）

每个动作必须有：

*   `pre`：执行前必须满足什么（不满足就 skip/repair）
*   `post`：执行后必须满足什么（不满足就 retry/escalate）

### ✅ 3) 可恢复（Retry / Repair / Fallback）

*   重试策略（次数、间隔、指数退避）
*   修复策略（刷新、重新定位、回到上一步、重新登录）
*   Fallback locator（主定位失败时备用定位）

### ✅ 4) 参数化（减少 token）

模板里只写“结构”，变动值用参数：

*   登录账号、搜索关键词、日期区间、金额、目标客户名等

***

## 2.2 一个推荐的 DSL 示例（YAML 风格，短且可审计）

> 注意：这不是代码表格，我用代码块给你看真实可用的结构。

```yaml
template_id: "crm.create_lead.v1"
description: "在CRM中新建Lead并保存"
params:
  customer_name: { type: string }
  email: { type: string, optional: true }
  phone: { type: string, optional: true }

guards:
  - ensure: "logged_in"
  - ensure: "on_app"
    app: "CRM"

steps:
  - id: open_create
    action: click
    target:
      role: button
      name_any: ["新建", "Create", "新規作成"]
    pre:
      any:
        - visible: { role: button, name_any: ["新建","Create"] }
        - visible: { role: link, name_any: ["新建","Create"] }
    post:
      visible: { role: dialog, name_any: ["新建Lead","Create Lead"] }

  - id: fill_name
    action: fill
    target:
      role: textbox
      label_any: ["客户名","Customer Name","会社名"]
    value: "${customer_name}"
    post:
      value_equals: "${customer_name}"

  - id: fill_email
    when: "${email} != null"
    action: fill
    target:
      role: textbox
      label_any: ["邮箱","Email"]
    value: "${email}"
    post:
      value_contains: "${email}"

  - id: save
    action: click
    target:
      role: button
      name_any: ["保存","Save","登録"]
    idempotency:
      key: "lead:${customer_name}"
      detect_duplicate:
        any:
          - visible: { text_contains: "已存在" }
          - visible: { text_contains: "duplicate" }
    post:
      any:
        - visible: { text_contains: "创建成功" }
        - url_contains: "/lead/"
```

你看这个 DSL 的优势：

*   **LLM 输出很短**（比 Playwright 代码短 5-20 倍）
*   执行是确定性的
*   具备幂等（`idempotency.key` + duplicate 检测）
*   可审计（每一步都可记录）

# 3) “模板化”怎么生成？（AI 不是每次都重写步骤）

我建议做成**两类模板**：

## 3.1 基础动作模板（低级、稳定、可组合）

例如：

*   `login.sso`
*   `search.by_keyword`
*   `open.menu_item`
*   `fill.form_fieldset`
*   `download.report`

LLM 只需要“拼装”这些模板，而不是重新发明定位逻辑。

## 3.2 业务流程模板（高级、跨页面）

例如：

*   `crm.create_lead`
*   `erp.submit_invoice`
*   `legal.upload_contract`

### 生成路径（推荐）

1.  **一次性录制（recording mode）**：让 LLM 或人工把流程跑通一次
2.  引擎采集：页面语义树（role/name/label/bbox）、关键网络请求、页面状态机
3.  LLM 把“录制轨迹”压缩成 DSL（编译）
4.  人工 review（可选），入库 versioned template

之后每次执行：只需要 `template_id + params`，token 立刻降下去。

# 4) Replay Engine 怎么做“成功率 + 幂等 + 可回放”

这里是关键：**把不确定性从 LLM 移到工程规则里**。

## 4.1 执行引擎必备能力

### A) 稳定定位（robust targeting）

*   主定位：role/label/text
*   次定位：相对关系（near/within）
*   末定位：CSS/XPath（作为兜底，不作为主方案）

### B) 等待策略（deterministic waits）

*   不用“sleep(2)”
*   用“等条件”：元素可见、可点击、网络空闲、特定请求完成

### C) 断言与校验（postcondition）

*   填写后必须能读回 value
*   点击保存后必须出现 success toast 或跳转 URL
*   失败则重试/修复/升级（escalate）

### D) 幂等机制（非常建议做成系统级）

**幂等不是靠“别点两次”**，而是靠：

*   每个业务动作有 `idempotency.key`
*   执行前查询或检测“是否已完成”（precondition）
*   执行后校验“是否真的落库”
*   遇到网络抖动或重复提交，能识别 duplicate 并转为 success

> 例如：创建 Lead 前先搜索客户名是否存在；存在则 skip 或 update。

### E) 事件与审计（回放与追责）

*   step-level log：start/end/inputs/locator used
*   截图/视频片段（关键节点）
*   Playwright trace（如你用 Playwright）
*   网络日志（重要接口）

# 5) “出现意外随时接手”怎么做得像样？

这块的关键点是：**接管必须进入同一个浏览器上下文（session）**，而不是另开一个浏览器。

## 5.1 触发“意外”的判定（建议分级）

### Level 1：可自动修复

*   元素找不到（页面布局变化）
*   短暂网络失败
*   toast 未出现但 URL 变化了

→ 自动 retry/repair，不打扰人

### Level 2：需要人确认

*   识别到验证码 / MFA
*   风控提示（“异常登录”）
*   关键操作二次确认（付款/提交合同）

→ 暂停，引导人接管

### Level 3：必须停止

*   账户权限不足
*   访问到不允许的页面（策略）
*   数据疑似错误（校验失败）

→ stop + 报警 + 工单

***

## 5.2 接管的实现方式（现实可落地）

你前面提的 iframe/canvas 都不合适；**接管基本就两条路**：

### ✅ 方案 A：WebRTC（体验最佳，延迟低）

*   服务器端把浏览器画面推流（tab capture / desktop capture）
*   前端 `<video>` 播放
*   前端采集鼠标键盘 → 回传 → CDP Input 注入
*   AI 暂停，锁住自动输入

### ✅ 方案 B：noVNC/Guacamole（最快落地）

*   Chrome 跑在虚拟显示（Xvfb）
*   用 VNC 暴露画面，Web 端 noVNC 交互
*   更像远程桌面，简单可靠

> 企业 PoC 通常先用 B，稳定后升级 A。

***

## 5.3 接管后的“回归自动化”

接管结束后，你要能让引擎继续跑：

*   重新做一次 `sync_state`：读取当前 URL、关键元素状态、登录态
*   从最近一个 step 的 postcondition 重新判断
*   继续执行下一步 or 跳转到恢复点

这要求你的 DSL 是“状态驱动”的，而不是“机械顺序驱动”。

***

# 6) 你这个方案落地的最小 MVP（建议 2\~3 周能跑）

## MVP 1：模板库 + 回放引擎（不带接管）

*   DSL 定义 + 解析器
*   基于 Playwright 的执行器
*   语义定位（role/label/text）
*   step pre/post + retry
*   trace + screenshot

## MVP 2：异常暂停 + 人工接管

*   引擎检测到验证码/MFA/关键确认 → pause
*   通过 noVNC 或 WebRTC 打开同 session
*   人完成操作 → 点击“继续” → 引擎同步状态继续

## MVP 3：模板编译（录制 → AI 压缩成模板）

*   录制操作轨迹（Action + 页面语义快照）
*   LLM 编译成 DSL（短输出）
*   review + 版本管理

# 7) 关键工程建议（决定你能不能规模化）

### 7.1 强推：让业务系统提供 `data-testid`

如果你能推动内部系统加一层稳定标识，你成功率会从“AI 玄学”变成“工程可控”。

### 7.2 模板要版本化 + 可回归测试

*   `template_id@v1/v2`
*   定期跑一批“金丝雀”用例
*   页面变更后快速定位失败的 step

### 7.3 权限与合规（你很在意的点）

*   浏览器 session 运行在服务器沙箱/容器/VM
*   参数与凭据走密钥库
*   全链路审计：谁触发、AI 输出了什么模板、引擎执行了什么、人工接管做了什么
