# 从已确认结果生成个人 Skill：统一设计 v1.0

日期：2026-10-21。状态：设计方案，尚未实现。

## 1. 产品约定

用户先完成一次任务并确认结果正确，再明确提出“把这个逻辑保存为 skill，叫做……”；系统据此生成个人技能，并在后续任务中复用。

用户的确认与保存指令是本流程的业务前提。生成时不再重新审计业务结果，也不要求用户重复确认；仅做技能包完整性、依赖和参数化检查。没有保存指令时，不自动把聊天内容变成技能。

这是一项通用的“从任务沉淀技能”能力，适用于表格处理、文档生成、报告整理及其他沙箱任务。表格统计是首个应用场景。

## 2. 用户体验

统一支持两个入口，两者调用同一套后端服务：

- 在结果消息上选择“保存为个人技能”，填写名称后保存。
- 对话中说“结果正确，把刚才的处理逻辑保存为个人技能，名称是……”。

流程为：定位来源任务 → 提炼可复用逻辑 → 生成标准技能包 → 安装到个人沙箱 → 返回保存结果。

来源默认是当前对话中用户正在确认的结果消息。按钮直接携带消息 ID；自然语言入口绑定明确引用的消息，或无歧义的最近一项任务。只有来源、必要参数或名称存在实质歧义时才补问。

保存成功后展示名称、用途、版本和“使用 / 查看 / 复制 / 导出”操作，例如：

> 已保存个人技能「按部门无偿统计」v1，仅你可见。下次上传新附件后，可以说“用按部门无偿统计处理这份附件”。

展示名称由用户决定。名称中的业务词不自动产生新的处理条件；实际执行逻辑来自已确认任务。

## 3. 保存的内容

保存一个可执行、可解释的处理方法，包括：

| 内容 | 保存方式 |
|---|---|
| 用途与触发场景 | SKILL.md 的 description 和说明 |
| 已确认的业务规则 | SKILL.md，必要时附结构化规则文件 |
| 输入要求与可变参数 | 说明必需文件、字段、模板及可覆盖参数 |
| 可重复执行的处理代码 | 按需放入 scripts/，优先复用已执行的有效代码 |
| 输出约定 | 文件类型、字段、展示方式及命名规则 |
| 模板和业务参考 | 按需放入 assets/、references/ |
| 来源、版本与归属 | 平台个人技能目录记录 |

原始附件、历史统计数字、完整聊天记录和临时文件路径默认不进入技能包。用户要求保留的模板可以作为 assets；模板与每次输入的数据附件需要明确区分。

生成器将一次性条件分成两类：

- **固定规则**：用户希望每次保留的分组、筛选、计算或排版规则。
- **运行参数**：新附件、输出名称、期间等每次执行时可能变化的输入。

不把原文件名、固定行数、旧列号、旧输出路径固化为下一次任务的输入。通过字段名称和已确认的匹配规则绑定新文件；无法唯一绑定时明确指出缺项，不猜测替代字段。

## 4. 标准技能包

每个技能采用一个独立目录，SKILL.md 是唯一必需文件：

```text
/knowledge/skills/<skill-slug>/
├── SKILL.md
├── scripts/          # 可选，确定性处理程序
├── references/       # 可选，业务规则、输入输出约定
└── assets/           # 可选，用户明确保留的模板
```

SKILL.md 使用标准的 name、description frontmatter。平台已有的 zh_name、triggers 可作为兼容扩展；归属和版本等管理信息存放在平台目录记录中，不成为其他运行时读取技能的必要条件。

例如，表格技能的最小入口可以是：

```markdown
---
name: department-amount-summary
description: 按已保存的部门分组与 WBS 筛选规则，汇总新附件中的金额。
---

# 部门金额统计

读取用户本次指定的附件，使用已保存的业务规则处理。
输入需要包含部门编号、WBS 编号和金额字段；保留来源金额单位。
具体规则见 references/rules.json；需要确定性执行时使用 scripts/run.py。
对新文件重新识别表头与数据范围，再执行筛选、分组和汇总。
输出分组结果、总计、处理条数和单位；用户要求文件时生成相应文件。
缺少必要字段或存在多个候选输入时，指出需要补充的内容。
```

上例仅展示包结构；生成时必须把具体的已确认规则写入包内，不能留下“参考历史对话”之类的外部依赖。

技能只需要说明即可完成时，不强制生成脚本。重复数据转换等需要稳定执行的任务，优先保留参数化程序；已有结构化执行计划也可以作为 references 中的执行配方，由适配器绑定当前输入后执行。

## 5. 共用架构与职责

```mermaid
flowchart LR
    U[保存按钮或自然语言指令] --> C[Skill Capture Service]
    C --> S[Source Adapter]
    S --> G[Skill Generator]
    G --> V[Package Validator]
    V --> P[Personal Skill Store]
    P --> L[Skill Catalog / Loader]
    L --> R[个人沙箱执行]
```

| 模块 | 职责 |
|---|---|
| Skill Capture Service | 处理保存请求、来源绑定、幂等、生成任务状态 |
| Source Adapter | 将不同任务的已确认过程转换为统一的 SkillSource |
| Skill Generator | 提炼规则、参数化代码、生成 SKILL.md 和必要资源 |
| Package Validator | 检查 frontmatter、引用、参数、依赖与脚本可运行性 |
| Personal Skill Store | 按当前用户安装、更新、复制、导出及删除技能包 |
| Skill Catalog / Loader | 维护元数据、发现技能、按需读取说明并绑定当前输入 |

共用流程不判断“这是部门统计还是合同处理”。新增任务类型通过 Source Adapter 补充来源提取，或复用通用沙箱适配器；存储、命名、版本、复制、发现和调用沿用同一套机制。

建议的统一 SkillSource：

```typescript
interface SkillSource {
  source: {
    kind: 'sandbox_turn' | 'execution';
    sessionId?: string;
    messageId?: string;
    executionId?: string;
  };
  objective: string;
  confirmedInstructions: string[];
  inputs: InputDescriptor[];
  reusableSteps: ReusableStep[];
  reusableFiles: ReusableFile[];
  outputContract: OutputDescriptor[];
}
```

这些类型是拟新增的内部契约，不是现有接口。具体任务的表达式、文档规则和程序保留在步骤载荷中；通用服务不再为每个业务场景新增特殊字段。

来源应结合用户明确指令、相关执行过程、有效程序及必要模板提取，不能只根据最后一段回复生成技能。没有可复用代码时可以生成说明型技能；代码缺失不等于不能保存技能。

## 6. 与现有系统的衔接

已存在的基础：

- personal-sandbox-runner 的 CUSTOM_SKILL_DIR 默认是 `/knowledge/skills`。
- skills.py 已扫描个人目录并读取 SKILL.md，支持个人技能发现与加载。
- Session Broker 已创建用户独立的 knowledge/skills 持久化目录。
- 现有 SavedSkillService 保存的是工作模式下冻结的多步骤计划，当前要求 deterministic_plan。

建议新增个人技能捕获与包管理服务，复用已有沙箱、技能加载和用户身份体系。界面可统一呈现“我的技能”，内部保留 `personal_skill` 与 `saved_workflow` 两种类型；个人技能生成不受“至少两个冻结步骤”的条件限制。

职责划分建议：

- **AI Orchestrator**：接收保存意图、取得有权访问的对话来源、组织生成。
- **Session Broker**：通过受控文件接口操作当前用户的个人技能目录。
- **Sandbox Runner**：提供来源过程、加载技能、执行技能所需程序。
- **前端**：提供结果保存入口、生成状态、个人技能管理和重新使用入口。

沙箱自带 skill-creator 的说明也应统一到这个约定：用户个人技能写入 `/knowledge/skills`；共享技能目录继续由平台管理。

## 7. 存储、安装与版本

技能包持久化在个人沙箱挂载的 `/knowledge/skills`，实际宿主机位置沿用 `data/users/<userId>/knowledge/skills`。容器重建后保留技能。

平台目录记录建议包含：skillId、ownerUserId、slug、displayName、description、aliases、version、sourceRef、packageHash、status、createdAt、updatedAt。用户归属由服务端登录态确定；自然语言和模型输出只提供名称、内容等业务信息。

安装流程：

1. 生成到当前用户的临时 staging 目录，不被技能扫描器发现。
2. 检查包格式、资源引用、参数和依赖；脚本型技能做必要的可执行性验证。
3. 为技能生成不可变版本快照和包摘要。
4. 安装当前版本并更新目录记录；在同一用户技能锁下完成切换，读取方使用已固定的版本。
5. 安装和加载检查成功后才返回“已保存”；失败时保留旧版本并给出可重试的生成状态。

版本快照放在不被普通技能扫描器遍历的位置，例如 `/knowledge/.skill-versions/<skillId>/<version>/`。活动目录保留标准技能包布局。读取与更新通过存储服务协调，避免执行过程中读到一半新、一半旧的资源。

同一个保存请求的重试返回同一结果。用户明确要求更新已有技能时创建新版本；另存为或复制则创建新 skillId。同名技能不静默覆盖。

## 8. 后续使用与复制

支持显式选择技能、按名称调用，以及现有技能路由机制按用途匹配。显式选择优先，名称有歧义时让用户选择。

运行时读取选定版本的 SKILL.md，绑定本次附件和参数，执行其步骤或程序，再交付本次结果。调用时的临时参数覆盖只作用于这一次；用户要求“保存修改”后才创建新版本。

复制包含两种操作：

- **复制为新技能**：复制规则和必要资源，生成独立 skillId，可改名称及规则。
- **导出技能包**：下载标准目录的 ZIP，可在其他兼容运行时使用；包内附明所需工具和运行依赖。

导出包默认不携带用户身份、会话引用、访问凭据及原始附件；这些平台管理信息与可复用内容分开存放。依赖平台专用能力的技能需要说明依赖，不能宣称所有导出包都能在任意环境直接执行。

## 9. 接口建议

下列为拟新增接口，均按当前用户隔离：

| 接口 | 用途 |
|---|---|
| POST /ai/personal-skills/captures | 从 sourceRef 和名称发起生成，支持幂等键 |
| GET /ai/personal-skills/captures/:captureId | 查询生成与安装状态 |
| GET /ai/personal-skills | 查询个人技能 |
| GET /ai/personal-skills/:skillId | 查看规则、参数、当前版本 |
| POST /ai/personal-skills/:skillId/versions | 从修改指令或新确认的任务生成版本 |
| POST /ai/personal-skills/:skillId/copies | 复制为独立技能 |
| GET /ai/personal-skills/:skillId/export | 导出指定版本 |
| DELETE /ai/personal-skills/:skillId | 删除个人技能并取消后续发现 |

生成状态统一为 queued → generating → validating → installing → ready，异常进入 failed。已有版本在更新失败时仍可调用。列表仅展示已安装可用的技能，生成中的项目展示进度状态。

## 10. 实施顺序与验收

第一阶段完成通用捕获、标准包生成、个人目录安装和显式复用；通过个人沙箱适配器接入表格案例。第二阶段补齐管理界面、复制导出、版本更新，再将文档等来源接入同一契约。

核心验收场景：

1. 用户确认任务后要求保存，生成个人技能并能在新会话中发现。
2. 同一技能处理新附件时重新计算，不沿用旧文件、旧行数或历史数字。
3. 名称和实际规则分别保存；重命名不会改变执行口径。
4. 无脚本的说明型技能和带脚本的处理型技能均可保存、加载。
5. 保存重试不产生重复技能；同名另存与版本更新行为明确。
6. 复制后的规则独立，修改副本不影响原技能；导出包能被兼容环境读取。
7. 容器重建后技能仍在；用户之间的技能、来源和文件相互隔离。
8. 安装失败不报成功，版本更新失败不损坏原有可用技能。
9. 文档类任务复用同一生成、存储、管理和调用流程，不引入表格专用主流程。
