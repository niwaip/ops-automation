# 文档参数语义提取方案最终建议

**版本：** v1.0  
**日期：** 2026-05-13  
**状态：** 建议采纳

> 本文是对前序设计文档的最终压缩版建议，用于回答三个问题：  
> 1) 这条方向是否值得做；  
> 2) 应该按什么方式做才不会把主流程做乱；  
> 3) 第一阶段是否可以开工，以及只应该做哪些内容。

---

## 1. 最终判断

**建议采纳这条方向，并且建议开工。**

原因不是“想把 AI 做得更强”，而是当前复杂文档任务已经暴露出明显的共性问题：

- 多 sheet、多数组、多条款任务在字段级参数提取下容易碎裂；
- `required_inputs` 容易混入模板循环标记、技术噪音和不合理类型；
- `waiting_input` 容易变成几十个字段的平铺阻塞；
- 明明可以预览的文档任务，也会因为参数表达方式不对而过早卡死；
- 这些问题不是某一个模板独有，而是会随着文档技能增多持续放大。

因此，**加强“复杂文档参数理解层”是必要的**。  
但前提是，这层必须被设计成**增强旁路**，而不是新的主流程。

---

## 2. 最推荐的方案

最推荐的方案不是“重写现有链路”，而是：

- **保留单一主流程**
- **在 Planner 内部为复杂文档任务增加语义提取旁路**
- **让 Execution / control-plane 继续作为唯一执行主线和事实源**

一句话概括：

> **主流程保持稳定，复杂文档的语义理解能力作为 Planner 和补输入解释阶段的可回退增强侧车接入。**

---

## 3. 为什么这是最稳的方向

### 3.1 它解决的是真问题

这套方案针对的不是“识别率不够高”这么简单，而是 4 类结构性问题：

- **字段噪音问题**
  - 模板循环标记、技术变量、重复字段直接进入 `required_inputs`
- **数组碎裂问题**
  - `items[]`、`deliveryItems[]`、`paymentSchedule[]` 被拆成大量叶子字段
- **阻塞过早问题**
  - 不影响预览的字段也被当成阻塞项
- **交互表达错误问题**
  - 用户更适合补“一个业务组”，不是补“二十个零碎字段”

### 3.2 它不破坏已有稳定链路

这条方案没有推翻现有主链路：

- 不新增第二套执行状态机
- 不绕过执行单
- 不绕过 `waiting_input`
- 不改掉 `submitInputAndResume()`
- 不让 Portal / Chat 成为新的事实源

这意味着：

- 老任务继续跑
- 简单任务不被拖重
- 复杂任务增强失败时也能回退到旧机制

### 3.3 它具备长期扩展性

如果后面要继续做：

- `groupedMissing`
- `previewReady / finalReady`
- 组级自然语言补充
- 数组样例骨架回流
- 文档专用理解接口

这条方向都能自然承接，不会返工主流程。

---

## 4. 必须冻结的原则

如果这个方案要进入实施，建议先冻结以下原则。

### 4.1 主流程只有一条

统一主流程固定为：

```text
用户输入
-> Planner
-> PlanDraftDTO
-> 创建执行单
-> waiting_input / queued / running
-> 执行 / 渲染
-> 结果产出
-> Chat / Portal 展示
```

### 4.2 旁路只能短暂插入

旁路唯一推荐接入点：

- `skill match` 之后
- `buildRequiredInputs()` 之前

旁路唯一推荐退出点：

- 回到 `PlanDraftDTO`

### 4.3 执行事实源不变

以下定义不变：

- `Execution` / `ExecutionStep` 是唯一执行事实源
- `submitInputAndResume()` 是唯一合法恢复入口
- `ExecutionDto` / `ExecutionStepDto` 是前端展示的唯一服务端事实来源

### 4.4 旁路必须可回退

任何时候都必须能回退到现有线上机制：

```text
semantic path
-> fallback to recognizeParams
-> field-level required_inputs
-> existing waiting_input
-> existing submitInputAndResume
```

---

## 5. 第一阶段建议开工范围

**建议开工，但只开第一阶段。**

第一阶段只做最小且最值钱的内容：

### 5.1 Planner 复杂度分流

- 简单任务继续走旧路径
- 复杂文档任务命中语义旁路

### 5.2 Planner 结果清洗与适配

- 去掉模板循环标记
- 去掉明显技术噪音字段
- 修正明显不合理的类型
- 输出更干净的 `required_inputs`

### 5.3 语义契约预埋

- `PlanDraftDTO.semantic`
- `ExecutionDto.semantic`
- `normalizedInputJson.semantic`

### 5.4 Portal 只读展示增强

- 展示 `groupedMissing`
- 展示 `previewReady / finalReady`
- 仍保留现有字段表单兜底

---

## 6. 第一阶段明确不做什么

第一阶段先不要做下面这些：

- 组级自然语言补充
- partial submit 后语义刷新
- 列表页与通知中心增强
- 预览联动策略
- 数组样例骨架回流
- 更重的文档专用理解接口
- 大规模重写 Portal 补输入页
- 改 control-plane 协议
- 改执行状态机

原因很简单：

- **先把主流程、承载契约和 Planner 输出稳定下来，比先做“更聪明的交互”更重要。**

---

## 7. 这条方案成功的标志

第一阶段不需要追求“所有复杂文档都智能补全”，只需要做到下面这些，就说明方向是对的：

1. 简单任务无回归
2. 复杂文档任务仍走统一执行单主线
3. `required_inputs` 中不再出现模板循环标记
4. 复杂文档缺失项更接近业务字段和业务组
5. 执行详情可展示 `groupedMissing / previewReady`
6. 旁路关闭后系统仍完全回到当前主流程

如果这 6 条都成立，说明架构方向正确，可以进入下一阶段。

---

## 8. 当前最值得投入的收益点

如果从投入产出比看，当前最值得优先投入的是：

### 8.1 先减少错误阻塞

比起“提高一点提取精度”，更重要的是：

- 别让模板噪音字段进入 `waiting_input`
- 别让不阻塞预览的字段过早卡死任务

### 8.2 先把数组当业务组处理

复杂文档最大的用户体验问题，往往不是单字段识别失败，而是：

- 清单
- 交付计划
- 付款计划

被拆成一堆没有业务语义的叶子字段。

### 8.3 先让系统表达正确

先做到：

- “缺的是标的清单”
- 而不是“缺的是 `items[].deviceName / items[].unit / items[].quantity`”

这个收益会立刻体现在：

- Planner 输出
- Chat WAITING_INPUT 文案
- Portal 执行详情

---

## 9. 风险与防线

### 风险 1：把旁路做成第二主流程

防线：

- 冻结单一主流程
- 旁路只在 Planner 和补输入解释阶段短暂插入

### 风险 2：control-plane 被迫承担文档理解职责

防线：

- control-plane 只透传 `semantic`
- 不在 control-plane 里实现复杂文档理解规则

### 风险 3：前端先走太快，反向绑架服务端

防线：

- 先冻结 DTO
- 先做只读展示增强
- 交互重构放到后续阶段

### 风险 4：简单任务被复杂方案拖慢

防线：

- 增加复杂度分流
- 简单任务默认不进 Subagent

---

## 10. 最终建议

综合前面的分析，我的最终建议是：

- **建议做**
- **建议按当前方案做**
- **建议先做第一阶段**
- **建议暂时不要扩大范围**

更具体地说：

1. 先确认“单一主流程 + Planner 旁路增强”这个方向
2. 先冻结 `semantic` 相关最小契约
3. 先在 Planner 中实现复杂度分流和结果清洗
4. 再做 `ExecutionDto` / `normalizedInputJson` 透传
5. 再让 Portal 只读消费这些增强信息
6. 等第一阶段稳定后，再考虑组级补输入和更深的语义理解能力

---

## 11. 一句话结论

> **这条方向值得做，且应该做；但必须以“单一主流程不变、语义增强旁路可回退”为前提，先把 Planner 输出质量和执行详情表达做对，再逐步升级复杂文档交互能力。**
