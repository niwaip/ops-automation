# 10:57 MCP 审核流程修复与验证

## 已完成的四项改动

1. **后续工具步骤约束**：每次只读契约披露都创建待执行步骤；首次调用成功后，新披露的工具仍绑定下一次调用。模型工具集合与派发允许集合保持一致，并在桥接网络请求之前检查 binding。同一强制步骤内的并行调用不能切换 binding 或重复执行。已发出的步骤即被消费，网络失败不强制重复；写入、未知副作用和待确认结果不进入自动执行。
2. **审核来源去重**：按规范化文档 URL 跨调用合并不同片段；优先正文，区分社区问答。最多 8 文档、单文档 5000 字符、总原文 20000 字符。每个片段保留实际 invocationId，所选引文不能错误归属到同文档的另一轮调用。来源页脚按规范化 URL 匹配答案引用，避免锚点差异导致无关来源混入。
3. **拒绝原因记录**：记录实际入选来源和裁剪状态、候选数、有效数、逐项拒绝原因及有界候选字段。原因包括 unknown_source、unknown_span、invalid_statement、quote_too_short、quote_not_found、community_not_configuration_authority、empty_claims 等。候选 credential 样式脱敏；模型阶段分别记为 mcp_answer_review / mcp_answer_review_repair，失败请求只记一次。
4. **零条通过后的有界补读与修复**：首次零条时，最多通过现有网关补读一个同 Skill 的只读文档，再审核一次。补读先刷新单工具契约并确认 effect=read；不使用其他用户凭证。整体审核恢复预算 40 秒，受任务剩余时间限制；每次审核最多 15 秒、补读最多 12 秒；无证据时仍返回明确的未核验提示。

新增逻辑分别放在 `mcp_review_sources.py`、`mcp_claim_validation.py`、`mcp_review_recovery.py` 等小模块，入口和 Agent 循环仅接入必要参数与约束。所有业务源码保持在仓库行数限制内。

## 真实故障注入揭示的额外根因

初版恢复验证中，MCP 搜索、正文补读均成功，但修复模型的 4 条候选全部在手写引文中插入省略号、移除 Markdown 标记或拼接句段，被严格原文比对拒绝。这次失败已独立保存在 `mcp-review-recovery-quote-copy-regression-2026-11-05.json`，没有将其作为通过证据。

最终实现改为 **选择稳定 source_id + span_id，由程序回填原始段落、URL 与 invocationId**。模型不再负责抄写引文；跨来源或未知段落编号明确拒绝。内部仍保留对兼容手写引用的严格匹配，程序不会把省略号当成原文。
