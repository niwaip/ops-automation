## 4. 直接根因：把字段名当实体值

`analysis_contract.py:335–339` 的命名实体正则为“部门 + 后续文字”，实际捕获：

```json
{"matched":"部门编码","captured_value":"编码"}
```

排除项包含“编号、姓名、名称”等字段词，但没有“编码”。程序因此生成 `entity_predicates=["编码"]`。

同一文件 `135–141` 的分组识别主要匹配“按……统计”等表达，原话“用 部门编码 统计”得到：

```json
{"entities":["编码"],"is_grouped":false,"group_dimension":null,"metrics":[]}
```

`analysis_task_state.py:164–175` 在“存在实体且不是分组”时要求实体过滤。执行回执真实存在的过滤是 `有偿无偿 in [有偿]`，分组是部门编号；它当然不含“编码”这个伪实体值，于是触发 entity_filter_missing。

这不是缺少特定部门筛选，更不能添加 `部门编号=编码` 来通过门禁。后者会改变用户口径并通常产生空结果。应将字段/分组维度与实体取值分开绑定，而不是继续扩充关键词排除列表作为完整修复。

## 9. 修复顺序与验收

1. **保留已确认的任务动作**：把读取/聚合/复制/写入/交付拆成结构化要求；执行能力不由 conversation/artifact 单独决定。不要用窄正则覆盖已有语义复核认可的写入任务。
2. **按完整任务绑定工具能力**：复合更新任务同时保留来源查询、更新规划、更新执行、状态与交付能力；后续只读分析筛选不得删除已获授权的写入能力。咨询和否定限制继续生效。
3. **区分字段与实体值**：“部门编码/部门编号”首先绑定当前来源字段；只有明确取值才形成实体过滤。分组粒度结合真实字段与计划确认，覆盖“用、按、以、按照”等自然表达及空格变体。
4. **复核只能推荐实际工具**：给复核输入当前工具目录与已成功阶段；不能推荐不存在的接口、反复读取已成功结构，或把修复建议当成新权限。
5. **完整更新门禁**：金额聚合通过仅完成一个子任务。还须有目标快照、对应部门/月份写集合、公式与计划保护、实际重算、最终文件和交付凭据。反事实复现已经证明仅解除实体误报会让分析门禁通过，但仍未执行更新。
6. **用本次原话走真实入口回归**：保留两份附件、1023、当月预测和部门有偿条件；在不硬编码业务金额的前提下，从任务识别一直检查最终下载工作簿。另测明确指定 FC 编码、只咨询不执行、缺映射、已有同名 Sheet、来源期间不符及目标原有错误。

用户不需要为了补偿代码而给“编码”添加一个筛选值。仅改说法或重试不能替代上述工程修复。对当前状态的准确说明应为：“部门有偿金额已核算，复制工作表和回填尚未执行；系统路由与验收发生错误。”
