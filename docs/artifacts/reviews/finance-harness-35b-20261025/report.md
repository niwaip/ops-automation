## 根因与责任边界

### P1：任务契约把算式误判为分组

F01 的“全年利润率按全年利润除以全年收入计算”，被解析为 `is_grouped=true`、`group_dimension=全年利润除以全年收入`，门禁继而要求各分组指标。

定位：`apps/backend/runtimes/personal-sandbox-runner/src/dsh_modules/analysis_contract.py:134` 的 GROUP_CONNECTOR/AGG_ACTION 正则，把“按…计算”当作分组意图，没有先验证该内容是否为真实来源维度。

已在同一运行容器仅调用 `build_analysis_contract`，无模型参与，复现相同字段。这部分是确定性的工程误判。F01 同时存在模型计划只返回匹配行数、未配置核心指标的问题，不能把整次失败全部归为门禁误报。

### P1：比例执行结果与门禁类型不兼容

F02 已返回正确事实：收入124020、毛利53443.25、营业利润21209.4、净利润16038.3、毛利率0.430924447669731。计划选择全年合计第16行，因此这里不是错误地平均12个月利润率。

毛利率计划写了 `unit=ratio`、`output_unit=%`，实际事实仍为 `unit=ratio`。查询执行器 `query_executor.py:489` 读取 unit，当前路径未根据 output_unit 转换；`analysis_task_state.py:127` 则要求百分比事实的 unit 必须严格等于 `%`。结果被错误呈现为“尚未执行毛利率聚合”，重复修复也未打通。

这是执行器、计划单位协议与门禁之间的衔接问题。修复时必须同步转换数值与单位，不能简单把0.4309改标签为0.4309%，也不能绕过数据门禁。

### P1：空值谓词与前文被误认作实体

F04 已执行部门空值筛选，并正确找出第28行。但契约解析器产生实体 `为空`、`证号重复的全部记录；`，随后门禁报告 `entity_filter_missing` 和 `unsolicited_filter_applied`，要求移除用户明确请求的筛选条件。

定位：`analysis_contract.py:363` 的命名实体正则以及 `:376` 的逆序组织实体正则。前者把“部门为空”的后缀当作实体值；后者可跨分号吸入前一个条件。无模型纯函数复现返回相同实体列表。

这部分是工程误判。F04 中模型也生成过一次不合法的前缀分组参数，且剩余三项查询未执行；因此整项归为工程误判与计划不完整并存。

### P2：技能准入与修复成本

F01–F05 均出现两次“技能准入字段不完整”后 fallback_to_general；F06 的 xlsx 准入成功。该现象与任务类型有关，尚未证明是工具 schema 缺陷或模型字段遗漏，暂列待定位，不能直接裁定为某一方错误。

F03 首次把绝对金额排序写成 absolute_relative_difference，被 comparison_plan_mismatch 拦截，随后修正为 absolute_difference，最终结果正确。此处是计划错误被工程校验有效拦截和恢复的正例。

F06 通过 read_file/bash/send_file 交付，独立数值验证通过，但 evidence_store 的 verified=false，因为没有 spreadsheet_evidence 类验收 guard。这与 F01/F02 的失败语义不同。说明当前 verified 标志不能脱离任务/产物类型解释，建议单独表达流程完成、数据核验和文件交付状态。

刷新后会话标题仍显示35B，输入框模型选择器变回 Auto；本轮六次调用全部发生在刷新前，实际命中模型已核对。后续是否保持显式模型选择，应单独回归。

## 下一步修复范围

1. 优先收紧任务契约：算式/计算口径与分组维度分离；空值、比较谓词与实体值分离；实体匹配不得跨分号吞入邻接条件。
2. 统一 ratio/百分比的计划、事实和门禁协议，转换时保留量纲与倍率。
3. 让“已算对但不可交付”和“缺少计算”具有不同错误码；有界修复必须补充真实工具证据，不能只让评审文字建议忽略告警。
4. 使用相同35B、原件哈希和本报告六个提示回归，不通过更换大模型掩盖工程问题。
