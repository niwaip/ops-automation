## 1. 结论

**这次真实生成了文件，11 个回填位置的数值正确，公式计算通过；但应评价为“带业务口径及保真限制的成功”，不能把 `verified=true` 理解为全部用户要求与所有格式都已独立验收。**

**Harness 的基本方向合理：模型负责理解、选工具和提出语义参数，工程负责计算、定位、编译、重算和发布。主要不足是契约未贯彻到底、领域映射侵入通用层、上下文管理粗糙、验收覆盖面窄。** 建议保留确定性执行内核，减少依赖文字提示维持的流程。

### 4.1 先解析用户任务，避免技能默认行为改写需求

`SkillRouter.route(..., load_skill_context=False)` 先给出候选路由；准入层随后调用 `extract_task_intent`。提取阶段传当前请求、必要用户历史、附件数量和可调用技能名称，不先把候选技能的全部业务规则灌进目标契约。

模型通过唯一函数 `submit_task_intent` 提交结构化结果。工程用 JSON、枚举、字段结构和用户原话匹配校验；随后再次请求模型复核 proposed_contract。两次使用同一模型，并非两个独立模型；第二次仍能看到初稿，能降低部分错误，但不能视为消除共同偏差。

### 4.3 工程将语义参数编译为坐标

## 7. 根因与责任划分

### A. 模板特定的别名被放进通用定位器（高优先级）

证据是 `layout_binding.py` 的 `SECTION_ALIASES`，包含精确模板字面量 `*P/*Y/EX（不含*L/*B）`，以及“有偿→直接”“无偿→间接”等规则。`locate` 按精确标题、别名、规范化/子串顺序匹配。

本次全部 15 条无偿记录事实上也是“直接”，说明分类维度不能互换。当前附件的无偿 WBS 都是 SP/IP 的 P 类形式，没有实测 L/B 类边界；本次金额一致不能证明别名完整复现模板排除口径。

归因：工程业务映射的来源与治理缺口。模型选择了“无偿”这一正确用户语义，但通用代码替它补了模板含义。建议将别名放到显式、带版本与出处的模板映射或业务配置，模型只能提出映射候选；若没有依据，针对该项提出具体问题。不要靠增加新业务词继续扩张全局字典。

### B. 目标业务键依赖来源命中，导致漏告警（明确工程缺陷）

`locate` 先找属于 `source_keys` 的目标单元格，使用首个匹配来源的行作为 `first`，随后只扫描该行之后的业务键。本次无偿的第一个来源命中是 FC46005 第 29 行，因而第 26、27 行的 FC48005、FC34032 被排除在目标键集合外。

这不是模型漏看部门，而是规划器构造的目标集合不完整。应先独立抽取完整目标区块键集合，再与来源做关联，计算 matched、target_only、source_only 和重复键；不能用有来源记录的行定义目标范围。

### C. 无来源策略没有形成可执行业务契约（混合缺口，工程为主）

工程默认保留旧预测并提示，本次 FC34022 使无偿总计高出来源汇总 2.87059 K。对于“预测更新”，保留旧预测有合理性；对于“全部重置为当月明细汇总”，缺失部门可能需要置零。用户没有明示这项策略，报告不能把其中一种当成事实性的唯一正确规则。

建议契约显式承载 missing_key_policy，并让回执列出保留值及总额影响。策略可来源于用户或已批准模板规则；没有依据时，仅就这一个会影响结果的歧义获取确认。不要为每一步工具操作重复索要批准。

### D. 任务契约与最终验收脱节（高优先级工程缺陷）

意图阶段保留了三个 requirements；语义计划却直接输出 `requirements={}`。执行协调器只遍历计划中已有的 requirements；空集合意味着没有任何逐项验收。本次回执的 coverage 和 evidence_refs 也为空。

此外，回执请求哈希来自：

```python
compute_request_hash({"req": plan_dict.get("task_contract_ref")})
```

实际 `task_contract_ref="current_turn"`。独立计算该 JSON 的 SHA-256，结果恰为回执 `d9e62bc936eca3eb51066a582e6f2ce8367cc717a95c05af702d34776e5d40dc`。这能证明哈希输入是固定占位符，不能证明回执绑定本轮请求。

`plan_hash`、`facts_hash`、输入/输出文件哈希仍有真实作用；问题局限在原始需求到计划和验收的关联没有闭合。建议保存不可变 TaskContract，带 session/turn、原始请求摘要、结构化期间/区块/单位/缺失策略/快照规则；计划必须引用其内容哈希，且每项要求要有执行操作或独立检查证据。

### E. 字体保真未纳入实际验收（明确工程问题）

实际文件已经显示历史/新表字体变化。即便门禁保护了数值及公式，也没有覆盖这些样式语义。当前较晚版本已有字体修复代码，但本审计没有验证修改后重新生成的文件，不宣称本次历史产物因此被修复。

建议按字体、字号、数字格式、边框、填充、对齐、合并、行列尺寸、打印设置及对象建立保真约束，并用实际发生替换的字体样本验证。对 LibreOffice 不支持的原生特性，应明确保留范围或采用避免全工作簿转存的发布方式。

### F. 通用文本读取协议不适合 Excel 分页（模型行为 + 工程接口）

模型在已有结构证据后仍反复读表，并提交越界文本行号，这是可改进的工具使用行为。工具接口同时允许 start_line/end_line 与 sheet/range，且空切片仍 success、显示行数元数据与返回正文不一致；默认截断的恢复提示也没有针对 Excel 区分文本行与单元格行。

应提供有类型的 `sheet + range` 读取，返回实际单元格覆盖、rows_returned、是否截断和 continuation；越界返回明确的 empty_range 或参数错误，避免伪成功。结构工具应直接返回完整候选区块、列层级、目标键概览和单位依据，减少读完整数值矩阵。

### G. 参数与耗时可观测性不足（工程问题）

TTFT 实际属于内部意图调用；前端 user/assistant 的 Redis timestamp 都在结束时写入，不能用两条消息时间差计算用户等待时间。各 HTTP 请求有独立 trace ID，但没有共同 phase/span 串起来；工具仅保存结果状态，没有耗时；模型只保留响应指纹及累计 Token。

建议分开 received_at、queued_at、execution_started_at、first_user_visible_delta_at、published_at、finished_at；为每次 LLM、工具、重算、验证、导出保存 phase、parent_span、duration、input/output/cached Token、实际 model/thinking 配置与字节数。日志中的下载访问 Token 应在记录 URI 前脱敏。

## 9. 建议的整体工程化方法

把已有模块整理为有边界的执行流程，而不是推翻重写：

```text
不可变 TaskContract
  → 附件和业务依据绑定
  → 只读 schema/目标区块发现
  → 可追溯 QueryPlan 与事实目录
  → 受限 UpdatePlan 编译
  → 候选文件执行
  → 数值/需求/保真验收
  → 发布清单与确定性摘要
```

### 优先级 1：先让“成功”含义可靠

- 修复目标键扫描，目标集合与来源集合独立生成；回归覆盖首部/中部/尾部缺失、重复键、来源独有键。
- 将 TaskContract 内容哈希贯穿计划、事实、回执，禁止更新任务带空 requirements 通过发布。要求“有偿 + 无偿”时，覆盖检查必须验证两个区块，不能仅验证有文件。
- 从通用引擎移走模板别名，记录模板映射出处、版本和用户确认；加入直接/间接与有偿/无偿正交的反例。
- 明确无来源的业务策略，最终报告列出来源汇总、保留预测影响、交付表合计。本例应直接显示 `140.60523 + 2.87059 = 143.47582 K`。
- 将快照名、业务 as_of、表头日期和数据期间分开建模。Sheet 名按本轮显式 1023；其他日期根据用户/模板规则处理，而非统一替成 today。
- 将字体和相关样式纳入独立保真检查。针对 14:41 的实际字体替换验证后续修复，不用“代码已加补丁”代替读回产物。

### 优先级 2：压缩回路和上下文

- 发现阶段返回紧凑的 typed schema：区块标题坐标、月份/指标列、键列与覆盖、单位来源、歧义；对本任务通常无需完整数值矩阵。
- 允许一次查询按“部门 + 有偿无偿”分组，再按区块引用对应事实；或者工程并发独立聚合，避免为两种分类各付一次模型往返。保持不同模板和类别可配置，不固定两个分类。
- 规划成功且没有歧义后，由执行状态机接管已授权执行；计划/执行仍分层存储，但无需模型只为转交 plan_id 再调用一次。
- 发布摘要从 receipt、变更清单及 reconciliation 确定性生成；需要自然语言解释时再用模型润色，文件名、数值、单位、告警不让模型重新编造。
- 工具全集证据落证据仓库，只向模型保留紧凑事实、覆盖摘要、证据引用和未解决问题；压缩历史工具正文，不能简单裁掉前 10,000 字符以外的关键范围。
- 避免对已经有哈希及本轮验证回执的文件重复扫描/重算；新增每个后处理 span 后再决定具体缓存点。

建议用真实模型回归设定优化目标，例如该类任务不超过 6–8 次模型请求、累计输入明显低于本次 261,869 Token，并在相同输出正确性下测量 p50/p95。这是待验证目标，不是已达成承诺。仅去掉第 11 次 plan_id 转交请求和第 12 次固定摘要生成，在本次轨迹中对应 11.627 秒模型时间；真实节省仍需对照实验验证。

### 优先级 3：让评测与发布可追溯

- 不只测试工具 happy path，覆盖用户原请求、单位补充、多区块、同名文件、日期冲突、未知业务映射及样式转换的完整会话。
- 基准文件应改变文件名、列顺序、目标布局、分类标签、业务键和期间，防止模板字面量“通过测试”。
- 单独度量意图提取的准确性、布局绑定准确性、计算正确率、目标键覆盖率、需求覆盖率、格式保真及交付声明一致性。
- 用故障注入验证：计划过期、来源变化、输出冲突、重算失败、缓存缺失、模型只说成功、缺一个区块时都能正确拒绝或报告具体未完成项。
- 记录 runtime/image/source manifest、prompt/schema 版本、模板映射版本、模型部署标识和生效参数。对输入大文件只记录受控引用与摘要，保持访问权限。
- 用少量真实模型端到端用例验证编排，再以确定性单元/契约测试覆盖组合边界；不应把所有布局组合都交给昂贵的在线模型重跑。
- 将大循环中的工具协议、任务推进、交付验收和各文档格式恢复继续下沉到明确模块，保持通用 AgentLoop 只负责调用与状态推进。
