## 上下文管理：本次实际发生了什么

### 历史完整，错误事实没有被验证

按当前运行代码和真实 Redis 问答离线重建，七轮带入历史为 0/2/4/6/8/10/12 条，长度分别为 0/1,125/2,947/4,568/6,230/8,409/9,401 字符。全部低于 16,000；单条历史回答均小于 4,000。没有整条历史丢失，也没有触发新加入的“保留头 1,200、尾 2,500”策略。

所以此次样本不能验证该策略对长回答的实际改善，更不能将错误解释为历史被截断。现有会话保留了最终文本，但没有将可供下轮核验的完整工具结果、计算来源、数据覆盖范围及事实状态作为独立上下文传递。虚构凭证以 assistant 历史进入报告，缺少失效和复核机制。未发现混入之前 19:44 会话的问答。

### 附件裁剪仍与提问无关

当前文件提取文本 16,369 字符，默认只注入前 12,000 字符及截断提示。离线重建的截断处在“交易明细”字段行中间，明细正文未进入该预览；管理驾驶舱正文同样在截断范围外。工作表目录虽保留名称，不代表正文已读取。

新加入的“每张长表先展示 30 行样本”减少了提取长度，但不能保证全局前 12,000 字符覆盖每张表，更不能支撑全表重复检测。第六轮没有追加 `read_file`、分页或 Python 统计，却作出了完整检查断言。

以上字符位置来自当前提取结果和留存 sidecar；由于第五轮已重算原文件，不能将其等同于前几轮原始 HTTP 请求快照。当前未保存逐请求 messages 快照。不过无论预览具体覆盖几条，30 行样本也不足以证明检查过全部 80 条。

每个 Excel 分析轮仍重复注入约 6,200 字符技能规范和固定附件前缀。第一轮只是列 Sheet，也使用 13,817 输入 Token。历史、附件、技能和工具结果分别限长，没有统一计入完整 messages、tools、输出预留以及工具循环增长的总 Token 预算。

### 工具路由部分修复，边界仍有缺口

当前代码重建结果：前四轮及第六轮 `inspect=true`，工具面为 read_file、bash、scan_knowledge、vision_inspect、web_search、fetch_page。原先“找出”“解释”进入全工具集的问题已经改善。

但“**检验**利润、现金和资产负债是否勾稽”仍为 `inspect=false`，开放全部 14 个工具，包括写文件、发送、提醒等与任务无关的能力。第五轮实际写入三个脚本并重算原工作簿。

即使进入 inspect 分支，所谓“受控 bash”目前仍是通用 shell，提示词中的不修改原文件约束不能代替执行层保护。应提供读取受限、在副本计算、返回结构化结果的工具。单纯继续增加中文关键词也不能解决原文件保护问题。

### 公式重算缓存存在独立可复现缺陷

`office_tools.py:77` 比较整张表的 `<f>` 和 `<v>` 数量，没有逐个检查公式单元格的缓存是否存在且非空。普通常量的 `<v>` 以及空 `<v></v>` 都会影响判断。

本次将工作簿复制到临时目录，仅在临时 ZIP 内清空全部 289 个公式缓存，保留有效的空 `<v></v>` 标签。调用现有 helper 后，它直接返回未计算的输入，甚至没有检查重算引擎、没有调用 subprocess。这证明检测算法不能可靠识别缺失缓存；不据此断言此次真实会话的自动缓存一定走了这个分支。

另外，先复制到最终缓存名、重算失败后不删除，而下次只看文件非空即可复用，会把失败副本当作已完成缓存。当前缓存签名只使用文件名、大小和 mtime，没有内容哈希或成功状态。建议临时输出、核验成功后原子发布，并验证公式缓存及重算结果。

## 建议修复顺序

1. **保护原文件并提供确定性计算工具。** 上传文件只读挂载或执行层阻断写入；在隔离副本重算，返回缓存是否可用、来源单元格、计算结果及错误。最大偏差、半年合计、重复凭证采用程序计算。
2. **对数据覆盖范围作硬校验。** 目录、样本、全表分别标识；重复检测必须读取全部记录。缺少证据时不得称“全面检查”，不得生成具体凭证行号及删除建议。
3. **保存已核算事实及文件版本。** 以内容哈希关联年度/月度指标、预算、勾稽差额与明细检查结果；后续报告引用这些事实。模型叙述作为未验证分析，出现矛盾时重新核算，原文件变更后旧事实失效。
4. **按问题取数并统一预算。** Sheet 清单只取目录和表头；半年分析只取相关月份及聚合；明细检查读取完整对应表。每次模型调用前统一计算 messages/tools/输出预留预算，减少重复规范。
