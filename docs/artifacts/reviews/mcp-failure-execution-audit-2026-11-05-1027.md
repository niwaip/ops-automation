## 3. 根因与代码证据

1. `llm.py:205`：收到正文流片段时，检测累计正文末尾的连续重复并抛出 ModelRepetitionLoopError。本次触发的是正文检测，而非思考链检测。
2. `agent_loop.py:344`：捕获该异常，记录 model_repetition_breaker，返回包含真实熔断原因的 final_text；不重试、不继续调用工具。
3. `runner.py:711` 和 `mcp_sources.py:11`：只要已选择 MCP 且没有成功的 call_external_tool 证据，就用固定文案替换 final_text。上一步的真实错误因此丢失。本次“检查连接状态”属于上一轮优化引入的错误提示缺陷。
4. `llm.py:358` 与 `model-proxy.controller.ts:183`：带工具的请求使用 stream_visibility=internal；代理将所有 SSE 帧缓冲至模型流结束后才重放（controller:367）。重复检测位于下游沙箱，无法在上游生成过程中及时熔断。本次近 120s 是模型代理请求持续时间，没有日志证明它属于 120s 超时。
5. `agent_loop.py:373`：仅 call_model_proxy 正常返回后记录响应遥测；第二轮提前抛异常，故没有 model_completed、usage 或响应指纹，callsLedger 只保留第一轮。exitCode=0 也只代表进程正常结束，不代表用户任务成功。

## 5. 建议修复顺序

1. 保留 typed failure / stop_reason；MCP 无证据门禁继续阻止无来源答案，但不得覆盖已有模型熔断、超时、鉴权等具体原因。只有实际连接异常才能提示检查连接。
2. 在代理接收上游流时执行有界重复检测，取消异常上游请求；保留内部缓冲避免重试输出重复，同时加入缓存大小和生成预算限制。
3. 在 finally / 失败事件中计入所有已启动模型请求的耗时与终止原因；中断 Token 未知应明确标注，不能补成 0。保留有界、脱敏的异常片段或指纹以便复核误报。
4. 对用户明确指定的只读 MCP 查询，通过执行状态约束下一步必须完成契约披露，成功调用前不得转入普通回答；保留不可用/歧义处理分支，不强制选择错误工具。继续遵守逐层披露，不把所有 Schema 注入提示词。
5. 回归覆盖“read_skill 成功 → 下一轮重复熔断 → 原因保留”“代理缓冲期间及时中止”“中断请求遥测计数”，然后再用同类真实模型请求重复验证稳定性。
