# 用户单位确认续执行与移除工数专用技能

日期：2026-10-24，Asia/Shanghai。改动保留在工作区，未提交 Git。

## 结论

`work-hours-update` 是此前引入的工数业务专用技能，与用户要求的通用 Excel 能力不符。本次已删除仓库技能及实际运行目录的副本，生产源码也不再按该技能 ID 选择能力。此前验证只覆盖了“缺单位时提出问题”，没有覆盖“用户确认后继续执行”，这是验证遗漏。

最终使用真实 `qwen36-35b-a3b` 验证了原会话续执行，并生成 [工数3Q预实管理_1023_2.xlsx](工数3Q预实管理_1023_2.xlsx)。独立读回检查通过，用户原件和已有同名旧交付物均未修改。不同字段、业务键、期间、布局及单位的变化版也完成了生成和独立检查。

## 原调用的工程原因

原会话为 `chat-session-1792772591655-nwaw70qz`。审计记录显示：任务契约已经将“k单位”保留为用户要求，但写入门禁只验证目标工作簿内的单位声明。用户确认没有进入执行上下文，因此模型无论如何填写 K 都会再次被拒绝。这不是用户没有回答，也不能归因于模型不理解 K。

另一处问题是续执行的工具选择：第二轮如果只检查“k单位”本身，就无法识别原工作簿更新任务，可能回落到旧的复杂聚合接口。实际请求还有“当前聚焦来源、早期参考目标”的包装文字，需要沿用真实用户原任务，不能丢弃原目标文件。

证据见 [原调用审计摘录](original-call-audit.json)。

## 修复方式

1. **通用能力接管。** 标准工作簿更新及其单位补充按用户任务契约选择原生更新引擎；不依赖工数专用技能。延续任务的要求清单即使只保留新增单位，也能从紧邻的原始用户更新任务恢复路由，跳过前面的单位答复。独立任务不继承历史目标。
2. **接纳用户明确确认。** 完整的简短单位回答按标准单位表识别，保留用户原话；不是只为 K 写分支。复杂表述由意图提取、独立复核及原话匹配绑定。规划工具中的 `target_unit` 本身不构成用户确认，来源单位也不构成目标单位依据。
3. **保持门禁。** 工作簿单位缺失但用户已确认时可以执行；模型猜单位仍被拒绝。用户确认与工作簿唯一声明冲突时返回具体问题。单位上下文逐轮清理，锁定计划保存用户原话依据。无需修改原表或补造单位说明。
4. **同名文件避让。** 实际工作区已有旧 `工数3Q预实管理_1023.xlsx`，本次默认分配 `_2` 文件名，Sheet 名仍为用户指定的 `1023`。显式指定冲突文件名时仍拒绝覆盖。
5. **可修复的参数反馈。** 实测中模型曾把期间值传入区块标题，旧提示引导其反复缩小范围。现在明确说明 `section`、`period`、`target_label` 的区别，并在这种错误出现时给出实际独立标题候选；不会按某个示例月份或业务标题自动改写参数。

主要改动位于 `user_declarations.py`、`task_intent.py`、`skill_admission.py`、`runner.py`、`agent_loop.py`，以及 `spreadsheet_update/` 内的路由、单位绑定、规划与工具说明。
