## 4. 工程问题与证据

### 4.1 步骤约束只覆盖首次外部调用

`mcp_execution.py:18`：只要已有任意 call_external_tool 回执，就返回原工具集合，不再强制步骤选择。第一轮搜索成功后，后续两次 fetch 契约披露没有绑定到下一次调用。模型继续用旧 search binding；因为该 binding 本身合法且已披露，网关无法判定这属于任务流程偏离。

因此，上一轮修复正确保证了起始披露及禁止无契约调用，但没有保证后续每次新披露与实际执行对应。本轮没有违反凭证或权限边界，却没有完成读取相关教程正文的目标。

### 4.2 审核输入按先到顺序截取，没有跨调用去重

`mcp_answer_review.py:33` 的 `len(sources)<8` 直接收集前 8 个有内容片段：本轮 3 次搜索共向模型披露 **13 个片段、6 个不同文档 URL（忽略锚点）**；审核只取得 **8 个片段、5 个不同文档 URL**。

具体为第一轮 5 个片段，加第二轮前 3 个片段；其中 3 个重复来源占了名额，第三轮搜索的 3 个片段全部未进入审核。第二轮后面的设备配置脚本文档也没有进入审核，尽管它出现在最终来源列表里。

第一项及第八项都是 Microsoft Q&A 的 Point-to-Site 回答；其余混合 VNet-to-VNet、S2S、证书认证 S2S 等场景。Q&A 在真实检索来源中，但不等于经过版本核对的官方教程。重复和场景混杂会降低审核质量，但现有证据不足以证明它单独造成了全部要点被拒绝。

### 4.3 “0 条通过”没有可诊断的明细，也没有恢复步骤

`mcp_answer_review.py:50–55` 对无效 source_id、字段/长度不符、quote 不匹配直接 continue。最后仅记录已通过的 claims；所有失败候选和分类统计丢失。该路径在 0 条时直接返回兜底，没有一次有界的修复或补读正文机会。

## 6. 建议优先级

1. **补齐逐次执行约束**：只读查询新披露某工具后，让下一步在该契约范围内执行；区分首次结果与任务证据是否已经足够，避免反复披露 fetch 却不断 search。继续保留权限校验、写入确认和分层披露。
2. **先整理再限量审核**：按文档及片段去重、保留补充内容，优先相关官方教程和已读取正文；记录审核实际选中的来源，明确 Q&A 类型和 VPN 场景。
3. **增加拒绝原因**：保存候选数和逐项安全诊断，如 unknown_source、invalid_fields、quote_too_short、quote_not_found；必要时保存有界、脱敏的引用片段或指纹。给审核请求正确的 purpose，保留终止与时延信息。
4. **零条通过后的有界恢复**：优先补取已选教程正文，或用带编号的原文段落修复一次引用，再审核；仍无证据时收窄回答或澄清连接场景，不放行无依据草稿。
5. **新增回归场景**：同一真实会话重试、首次成功后披露另一工具却仍调用旧工具、跨调用重复来源挤占审核额度、全部引用校验失败后的诊断与恢复。
