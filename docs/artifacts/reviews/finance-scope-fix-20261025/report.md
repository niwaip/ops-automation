# 查询、派生计算与来源口径修复

## 已完成的修改

- 复用 SemanticContractJudge 识别用户要求的业务指标与期间。修正行式报表提示，避免将年度金额列替换成唯一业务指标；合约缓存升级到 v4。
- 合约裁判返回期间时，显式要求复核实际来源，不再用“是否存在月份 WHERE”替代期间判断。复用 SemanticFilterJudge，只提供实际取数列、执行范围、过滤、来源哈希和选中行摘要；期间匹配没有新增固定年份、表名、科目坐标或日期正则。
- 来源裁判不再看到未引用的其他期间列，避免凭“表内存在目标列”猜测执行正确。复核缓存升级到 v3，包含实际表头、来源绑定和工作簿哈希。
- 无法确认来源口径时返回 source_scope_unverified，明确冲突时返回 source_scope_mismatch。合法科目选行不会再因 has_filters=True 被无条件清空；业务过滤的结构回退也不能豁免未确认的期间。
- query 与 calculations 现在分阶段执行。声明的计算必须成功，才能返回组合成功回执；不再静默漏算。计算来源只能位于查询最终事实的单元格中，不能读回 WHERE、HAVING 或 LIMIT 排除的数据。单一来源 query 事实可使用精确 ref；旧式聚合编译成 query 度量时不会重复执行。
- 查询后计算与原生查询保留各自计划、覆盖和来源；派生结果参加门禁与正文展示。明确的除法等算术表达式不再被未分组混加检查误伤。
- 复核不能仅拿其他指标的事实撤销某个漏算指标。数据哈希、单位、源坐标和数学计算仍由程序验证。

新增职责模块为 analysis_scope_context.py（裁判来源上下文）和 query_calculation_stage.py（查询后计算）；现有执行器只增加阶段集成。同步更新工具描述与运行时 README。

## “2026”如何被识别

有真实附件表头且模型代理可用时，build_analysis_contract 调用 LLM 合约裁判，从用户原话中提取 period 和全部业务指标。新的 requires_source_scope_review 标志由该裁判返回的期间触发；随后来源裁判判断实际读取的列/行条件是否满足请求期间。

例如，用户要求某年数据，真正读取该年的实际列可以通过；读取另一年实际列时拒绝。判断来自 LLM 对请求和实际绑定的理解，代码没有新增“遇到某个年份就放行”的规则。既有无附件/离线结构化兜底仍保留，新加的来源匹配逻辑不依赖它猜测期间是否正确。

## 验证

相关回归共 **149 项通过**，结果保存在 regression-tests.txt。覆盖真实 LLM 合约返回形态、无业务过滤但有期间、科目选行、自动补算、混合计划、精确 ref、WHERE/LIMIT 外来源拒绝、错误期间、不可判定、旧聚合兼容、缓存隔离、错误布尔类型与漏算指标不能被其他事实豁免。

完全合成数据的真实模型验证通过，见 synthetic-live.json：

- 模型独立识别测试期间及四个业务指标。
- 查询后注册补算成功，最终门禁 complete=true。
- 同一计划 query+calculations 成功，最终门禁 complete=true。
- 故意改成错误年度列，来源裁判返回 matched=false，并产生 source_scope_mismatch。

合成用例只发送脚本生成的测试指令、表头和证据，不读取用户附件。独立原附件在线复测被自动审批拒绝，原因是会将用户附件派生信息发送到模型目的地；本轮没有绕过该限制，也没有改写用户聊天历史。

语法检查与 git diff --check 通过。运行沙箱实际导入文件的哈希与当前源码一致，记录于 runtime-hashes.json。dsh 是每次请求启动的新进程，使用挂载源码；无需重启 Orchestrator/Broker。验证期间个人动态沙箱被空闲回收后重新启动，再完成测试。

## 当前边界

query 混合阶段支持 calculations；checks、rules、profile_tables 使用独立调用，混入查询时明确报错。多来源 query 事实不直接 ref 成一个猜测数值，需提供明确的来源聚合表达式。模型不可用或无法确认期间时继续阻止无证据的完成声明。

没有提交 Git commit；保留工作区其他已有改动。
