## 4. 工程问题、原因和证据

### P1-A：已发布文件不能替代最终说明的事实校验【本次已发生】

最终文字的错误旧值可直接与原件及回执对照。模型生成错误文字是直接触发点；这里没有把直接错误改称纯工程计算错误。但 harness 放行未经结构化证据校验的金额陈述，是应修复的工程缺口，无需以模型规模解释或规避。

`final_answer.py:56` 能生成确定性 published_summary，但它主要作为兜底；正常长文本仍可保留模型自写数值。`agent_loop.py:703` 的更新门禁主要判断是否 published；`final_answer.py:282` 在存在 verified 产物时还会抑制某些核算未完成告警。防止错误地说“没交付”是合理目标，但不能顺带把全部文字事实视为正确。

此外，本次计划已有 reconciliations，公开 plan/execute 结果只返回预览、summary、warnings，没有把完整对账结构传给最终呈现。工程算出的事实停在内部计划，模型仍在大段历史中自行组织说明。

**改进：** 从实际发布回执、已绑定区块、旧值/新值、保留影响和对账结果确定性生成数值表、警告和文件信息；模型只润色不改变事实的解释。结构化事实需要始终带 section、key、period、unit，不能只带部门编号。`verified` 分成数值、需求、格式、交付和文字一致性各自状态。

### P1-B：需求覆盖与请求身份没有贯通【本次已发生】

本次 plan.requirements 已不是空对象，说明相对历史版本有进展，但仍是生成器从自己已有操作反推的 `copy_sheet` 与 `update_forecast`，没有绑定三段真实用户要求。`turn.py:302` 的 executed_op_ids 取自计划中的操作清单，不是独立执行账本；校验目标主要是“这个 ID 有没有在同一计划中定义”。数值读回检查仍有价值，但不能证明所有用户要求都已覆盖。

`semantic_plan.py:239` 默认 task_contract_ref=`current_turn`；`turn.py:437` 对 `{"req":"current_turn"}` 算哈希。已独立重算并得到与回执完全相同的 `d9e62bc9...`，证明它没有绑定本轮真实请求。回执的需求覆盖及证据引用均为空。

内部生成器支持 requirements/task_contract_ref，公开工具 schema 却没有这两个参数；正确修复应由服务端注入真实契约，不应要求模型复制哈希或内部操作 ID。

**改进：** admission 生成不可变 TaskContract 及真实内容哈希，服务端贯穿 plan/facts/receipt。验收器从真实要求推导必须覆盖的区块、期间、单位和快照规则，对实际执行和读回结果逐项给证据。少一个分类、只分析没交付、期间错误、计划被改写都不能通过。

### P1-C：业务映射从代码移入记忆，但依据验证与作用域仍不足【本次依赖 + 反例复现】

定位器已不再内置历史审计指出的模板别名。本次目标 A22 是 `*P/*Y/EX（不含*L/*B）`，本轮 section_confirmation=null，而工作区 [domain-knowledge.json](domain-knowledge.json) 的 general 存有“无偿 → 该标题”。按当前定位器的实际匹配路径，该记忆使本轮免于重新确认。

记忆有 `source=user_confirmation` 和 quote，但没有确认会话、turn、时间、模板身份和撤销状态；本次计划也未保存使用了哪条映射。仅凭这个 source 字段不能独立证明用户在哪里确认过，本审计不据此认定确认是伪造的。

[probe_harness.py](probe_harness.py) 在临时工作区复现：

1. `user_declarations.py:97–110` 即使 ground_user_quote 返回 None，仍回退保存原 quote。用户只说“请更新本月预测”，传入“用户从未说过的确认”仍被接受。
2. `direct_section_reply` 对“不要确认 ABCXYZ”，候选 `[ABCDEF, ABCXYZ]` 返回 **ABCDEF**。原因是字符集合交集达到 3 就匹配第一个候选，既不要求精确匹配，也不处理否定。
3. `domain_memory.py:56–63` 在传入完全不同的文件哈希时仍回退 general，套用其他模板的映射。
4. `user_declarations.py:56` 还残留 `asked_section or '无偿'` 的业务默认值；通用确认解析器并非完全无业务硬编码。

**改进：** 确认必须来自可信用户消息并能追溯，失败即不持久化；精确且唯一地绑定候选，否定/多候选/不明确进入待确认状态。记忆按用户及模板身份/布局签名限定，内容哈希用于版本证据，不能靠文件内容一变就重新学习，也不能无条件跨模板回退。跨模板泛化规则需要单独明确的适用范围。读取失败、失效、冲突应作为结构化事件留下，不能全部 except/pass。记忆写入用原子替换和版本检查。

### P1-D：目标区块边界由来源键反推，可跨到其他区块【当前源码反例复现】

`layout_binding.py:121–179` 找到标题后，先在直到工作表末尾的区域内搜索来源键，再据这些键和重复表头推断边界。目标区块还没有被独立闭合，来源键已经参与定义边界。

隔离探针建立两个区块：销售在 A1，服务在 A6；销售只有 SALES_ONLY，服务才有 SERVICE_ONLY。请求定位销售、来源键 SERVICE_ONLY 时，`locate` 返回 `region_id=销售`、`SERVICE_ONLY→第9行`，实际第 9 行属于服务。

这证明定位器存在跨区块绑定，不表示本次 11 格发生了跨界，也不把定位器探针说成完整发布攻击演示。本次数值和坐标均已独立核对正确。

**改进：** 先依据工作簿结构独立形成闭合目标区块，再在区块内发现完整目标键集合，最后与来源键做关联。无匹配、重复键、来源独有键明确报错/按策略处理。不能因为在下一段发现了匹配键而扩大当前目标范围。应覆盖前置、尾部、零交集、相同键跨区块、多级表头及仅一个匹配键的反例。

### P2-A：对账是计划算式，尚非独立发布验收【本次结构证据 + 反例复现】

本次算出的 `140.60523 + 2.87059 = 143.47582 K` 正确，但 `compute_reconciliation` 把 delivered_total 直接定义为两项相加，再固定返回 is_balanced=True，没有从输出文件读取实际控制总额。这是合理的“预期对账”，不能单独称为已执行的平衡校验。

`semantic_plan.py:199` 把无来源且为公式的旧值当作 0；`reconciliation.py` 与警告逻辑用 `>0` 判断“非零影响”，负数保留项不会被标记。临时探针对 -5 K 保留值返回 has_impact=false，虽 delivered_total=95。

**改进：** 区分 expected 与 observed，发布前读回对应总计或独立按目标键求和，比较差值和容差；用 `!=0` 识别影响。公式旧值应读取验证过的缓存或拒绝未知，不能静默置 0。把“无明细保留/清零/阻断”做成有依据的策略，最终清楚披露。

### P2-B：流程靠提示推进，重复计划未受幂等约束【本次已发生】

UPDATE_INSTRUCTIONS 已反复要求拿到 plan_id 后立即 execute，本次仍发生成功规划→重复无偿聚合→重复规划。两个 run 的计划哈希与幂等键相同；第一份计划仍 planned，第二份 published。已有同名文件导致名称递增为 _14，**并不是本轮执行重试 14 次**。

`tools.py:56` 每次规划新建 Coordinator；`turn.py` 保存 idempotency_key，但这条路径没有按它复用既有 run。`tool_dispatch.py:185` 将读取类第一次重复拦截，但 aggregate 不在这一集合里，且重叠范围、语义等价 JSON 本身也需要更高层规范化。已发布同一 plan_id 的 execute 会核对哈希并复用，这是应保留的局部幂等机制。

**改进：** 将任务执行作为显式状态推进。规划完且没有未决问题时，由已授权的执行状态自动调用执行器；plan 和 execute 仍作为独立可审计边界保存。规范化 query+输入版本、plan+contract 生成幂等键，读缓存/复用计划，明确旧计划 superseded/abandoned，避免仅靠循环次数和文字警告。

### P2-C：已有状态枚举未形成完整恢复协议【源码可见风险，未故障注入】

实际 phase_history 只有 discovered→planned→published；prechecked/applied/recalculated/validated 没有留存，candidate_path/hash 为空。`state.py:145` 只验证状态名称，不校验合法迁移关系。

`turn.py:386–454` 依次移动候选、复制工作区产物、写 receipt、更新 published 状态；中间存在进程中断窗口。若文件已可见但回执/状态未提交，再试可能遇到“输出已存在”而无法自动恢复。这里是源码推导的恢复缺口，本轮没有杀进程或人为破坏生产任务来验证。

**改进：** 为阶段输出持久化 manifest，维护候选/发布哈希，明确允许的状态迁移。使用准备发布清单、原子落盘与可恢复提交步骤；相同幂等键重试时按内容哈希确认已完成产物，避免一概拒绝存在文件。外层用户锁本轮有效，但它不能替代事务恢复协议。

### P2-D：样式修复仍有启发式，保真验收范围偏窄【本次字体名已通过，泛化风险未完整验证】

`executor.py:143` 在 LibreOffice 后统一替换 DejaVu Sans，优先使用“等线”，否则从源字体集合中取一个。它不是逐样式映射，对多字体模板可能把不同原字体映射为一个字体；集合取值也缺少明确选择依据。本次没有字体名变化，不应继续把历史问题当成本轮失败。

`diff.py` 主要比对值和公式，没有完整检查样式、对象与打印设置；当前 PreserveSpec 中的愿景不等于全部执行。公式健康的 provenance.output_hash 早于字体修复，实际最终发布哈希不同。应记录变换阶段及对应哈希，保证最终产物仍有清晰校验链。

**改进：** 对模板资产选择有定义的保真策略；尽量恢复原字体/样式映射而非全局替换。保留型更新的验收包含需要保持的样式、合并、条件格式、验证、对象及页面设置，区分等价序列化差异与实际视觉变化，补少量原生 Excel 或渲染验收。

建议架构保持通用执行层与领域层边界：

```text
TaskContract（真实用户要求与权限）
  → GroundedBindings（附件、单位、区块映射及依据）
  → WorkbookSchema（独立目标边界和键集合）
  → QueryPlan / FactCatalog（可追溯计算事实）
  → UpdatePlan / Compiler（受限写集合）
  → ExecutionJournal（候选、重算、验证、恢复）

  → PublishedManifest（最终文件哈希）
  → ReceiptRenderer（与证据一致的交付说明）
```

无需推翻所有模块，也不建议增加一个包揽全部业务的大审核模型。让工程处理可确定的计算和完整性，模型处理语义意图及真正的歧义。

## 7. 分阶段改进与验收计划

用户允许分阶段推进。本轮完成全链路证据和边界风险基线，后续应按依赖小步落地，每阶段单独验证，避免把现有未提交改动一并当作已验收。

| 阶段 | 工作 | 通过标准 |
| --- | --- | --- |
| 第一阶段：阻止误绑定和无依据记忆 | 闭合区块后再关联键；严格用户确认；模板作用域 | 本轮五个反例改成拒绝或正确结果；不存在跨区块写入；正常用户确认仍可复用 |
| 第二阶段：使“完成”可验收 | 真契约贯通、分类级需求覆盖、输出读回对账、确定性摘要 | 缺一个分类/错误月/错误单位不发布；回执覆盖非空且可追溯；最终金额不与文件矛盾 |
| 第三阶段：幂等与恢复 | 查询缓存、计划复用、状态迁移、可恢复发布 | 同任务同输入不重复 run/文件；在候选、重算、发布各阶段中断后正确恢复 |
| 第四阶段：性能与泛化 | 紧凑 schema、结果压缩、消除无用往返、phase/span | 相同正确性下对照 p50/p95、累计 Token、工具及 LLM 次数，定位慢请求；不以单次改善宣称全局稳定 |
| 第五阶段：保真和长期回归 | 样式/对象策略、版本 manifest、真实模型小样本端到端 | 更名、换列、换布局、跨月、多表、负数/公式保留项、未知映射均覆盖，模型与工程版本可定位 |

修复时按职责拆分，不向 agent_loop 继续堆通用流程特例。后端若修改需按实际运行方式决定重载；本地当前 dsh 模块 bind mount 对下一进程可见，长运行服务的改动仍需按仓库 Docker 入口重启并验证，不能仅凭源码已改宣称运行已修复。
