# 个人技能语义门禁落地验证

2026-10-22。本目录含用户业务数据与执行证据，仅保存在本地。

## 根因与落地

原流程通过描述词亲和度选中 dept-summary（审计重放得分38.854），runner 随即提前执行固定技能。它只用关键词判断新口径，漏掉“合计超过500k”；LLM 只负责在旧结果中选择解读事实，没有审核技能适用性或本轮目标。算术通过与任务完成被错误地合并成了同一标记。

当前增加模型执行前准入与执行后独立验收。未明确调用技能的匹配只提供能力参考，不注入默认业务规则正文。明确调用时生成当前附件的保存规则查询模板，临时条件叠加到 query，原技能包保持不变。原样模板继续使用可信固定引擎，其余复用原有查询引擎的 WHERE/GROUP BY/HAVING/排序/分页。

门禁采用无副作用的原生结构化函数，要求引用用户原话、绑定有效查询节点。最终验收需引用当前回执ID且覆盖全部要求；通过后才生成表格或发送结果 delta。验收拒绝或计划无效时反馈缺项，最多重新规划、执行和验收一次。失败或未确认的历史尝试不能混入成功 evidence_ids；来源与回执完整性仍由程序检查，模型无权豁免。

真实模型接入过程中确认：自由 JSON、未内联的条件 schema、含混的“保存/临时”模式以及冗长审核理由都会降低小模型的输出稳定性。最终使用统一 query 契约、真实节点枚举、内联条件字段、简短审核原因代码，并让未选中的候选业务规则退出审核上下文。无效响应均被拦截，没有返回未经当前任务验收的表格。

## 最终真实验证

模型沿用用户本轮配置 qwen36-35b-a3b，无替换模型。原附件 SHA256 `5d5b57bdcb5e3257b93ccd4e2f5b194e96c3c573e651b93799c3dec2ec8d5374`，验证前后相同。

| 场景 | 结果 | LLM调用 | 耗时 | 验收 |
|---|---|---:|---:|---|
| 原始问题，未指定技能，合计超过500K | FC45031，677.58544 K；274条参与聚合 | 2 | 7780ms | accept |
| 明确使用技能并追加500K阈值 | FC45031，561.75345 K；253条参与聚合 | 2 | 7483ms | accept |
| 明确使用技能，只要表格 | 七个部门，分组金额之和1637.41990 K；253条参与聚合 | 4 | 15929ms | 首次revise，重新规划后accept |

第三项的最终输出无需全表总计字段，独立 Decimal 重算七个返回值确认其和准确。原回放脚本最初把“必须出现总计文本”误作测试要求，此检查与用户“只要表格”的要求无关；随后改为核对回执中的分组金额之和，并在 live-validation.json 中独立验收三项实际结果。没有通过放宽业务规则来使结果通过。

“只要表格”不跳过语义门禁；没有使用“关闭LLM以追求速度”的成功捷径。结果展示使用业务列名与可读条件，不向用户输出 query 内部结构。

## 范围与限制

适配范围为个人 verified_workflow 表格技能，当前预检绑定单一 XLSX/XLSM 业务表。其他技能执行引擎继续沿用既有门禁，不能宣称所有技能都已获得相同语义验收保证。模型语义审核仍可能误判；失败关闭、结构化计划、独立计算、再次验收和有限修复是影响控制，不是语义正确性的数学证明。
