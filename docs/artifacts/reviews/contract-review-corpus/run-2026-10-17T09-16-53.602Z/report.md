## P1 工程问题一 DOCX 回退分段丢失正文却成功交付

18/18 DOCX 均缺失正文。示例 `CT01-zh-docx` 的采购合同原有 8 条标记，最终只保留 A08，其余 A01–A07 消失；只有前言和第8条共2节点。仍然 `succeeded`、`isTruncated=false`、`warnings=[]`，风险条款未进入模型审查。

证据：该例 `execution.json`、`output.json`；同份文件直接解析对照 `parse-probe-docx.json` / `parse-probe-pdf.json` / `parse-probe-txt.json`。三者在线解析分别返回 2/9/9 节点。PDF 与 TXT 全部 8 个标记保留；DOCX 的 `fullText` 只剩前言和签署区，A08 正文仅留在标题。

根因链：

1. DOCX 的条号、唯一标记和正文使用一个 Word 段落，内部用软换行。这是正常有效的 DOCX 布局，TXT、DOCX 和 PDF 的原始文本已作一致性核验。
2. OpenXML 解析器拼接 run 时忽略换行，再用长度与句末标点限制条款边界，结果形成一个大节点。日志明确记录 `OpenXML direct parsing produced only 1 monolithic clause ... Attempting Mammoth fallback`。
3. `contract-ast-parser.service.ts:126-158` 因节点数量选择 Mammoth HTML 回退。
4. `contract-clause-segmenter.util.ts:151-187` 将以条号开头的整个段落放入 title，content 保持空；`:68-70` 仅保存 content 非空的前一节点，于是连续第1–7条被丢弃。最后第8条因后续签署段落使 content 非空才保留。

磁盘编译模块单独解析保留全体标记，与在线结果不同，已查明是上述回退分支造成，不能据此宣称服务未加载新版本。证据 `compiled-docx-probe.json` 与 `diagnostic-log.txt`。

建议：保留 Word 软换行；边界和正文拆分不能吞掉同段内容；选择回退结果时比较文本覆盖率，不能只看节点数量。无论是否允许单节点文档，正文覆盖不足都必须阻断或明确降级。

## P1 工程问题二 模型选择未贯穿识别器 立场丢失或反转

`multi-node-parameter-binder.service.ts:282` 向 recognizeParams 传 `{ model: modelId }`，而 `recognizer.service.ts:167` 读取 `dto.modelId`。已指定的 35B 未进入识别器选型，识别器走默认模型。

证据包含执行单 `inputJson.__promptDebug`：42 例记录 `User location is not supported for the API use`；12 例成功识别调用的 modelId 为 Gemini UUID。审查阶段独立业务账本仍是 Qwen 35B，两个阶段不能合并声称“全是35B”。

34 例未通过既定立场断言，其中多数输出 buyer 但来源为 default，说明没有可靠绑定用户立场；另有明确反转：`CT05-ja-txt` 用户是委托方，结果 seller；租赁三个 TXT 均输出 seller，而请求是承租方。来源字段 user_confirmed 不能证明事实正确。

建议：统一 DTO 的 modelId 字段，选定模型贯穿识别、规划与审查；用单次 execution 的阶段模型清单验收。区分用户原始角色、模型推断、默认回退；必需参数识别失败不能悄悄按默认角色完整执行。
