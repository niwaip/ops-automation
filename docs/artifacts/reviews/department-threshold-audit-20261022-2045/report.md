## 根因及证据

1. **相似问题被自动当成固定业务规则的调用。** `skill_router.py:869` 采用亲和度选择技能。用实际请求和此前会话历史只读重放，得分 38.854，理由 `desc_terms(38.9)`；用户没有指定技能，但最终 skill_id 为 `dept-summary`。词义相似不足以证明用户接受它附带的 WBS 排除口径。

2. **当前条件未进入可执行计划。** `runner.py:340` 在普通分析循环前执行个人技能并直接返回。`personal_skill_workflow.py:16` 用关键词判断新口径，漏掉“按…统计”“合计超过500k”；实际重放该函数返回 false。随后第 77–80 行读取并执行保存的 workflow.json，它只有部门分组、金额求和和 WBS 前缀排除，没有本轮阈值。固定引擎 `personal_skill_workflow_engine.py:26` 的 schema 也不支持聚合后的 HAVING。回执明确包含全部七个部门，无任何 >500 条件。

3. **校验范围与完成声明不一致。** 原表摘要、行数守恒、分组总额和保存时复算全部正确，因而 `personal_skill_workflow.py:106` 接受证据。`evidence_store.py:22` 基于该 accept 标记本轮 verified。系统没有核对“用户请求中的每个条件是否已被执行”，却输出“已完成核算并通过校验”。这是计算正确但任务未完成的假阳性。

4. **LLM 参与层次不足以纠正问题。** `personal_skill_presentation.py:88` 限定模型只能选择已验证 fact ID，禁止计算或调用工具；它返回并被接受的是 `largest`、`top_two_share`。事实列表没有阈值结果或请求未覆盖项，模型无法生成正确的筛选回执。最高部门与占比本身并非捏造，但不构成本轮请求的答案。主因在工程执行契约，不能归因为模型算错或完全没有调用模型。

这是此前“固定流程可验证执行 + LLM 解读”接入仍遗漏的运行时语义适配：只保证已保存规则执行准确，没有保证本轮自然语言被完整落实。五个相关沙箱模块与当前本地源码的 SHA256 全部一致，不能用容器仍运行旧代码解释此问题。

## 修复应满足的验收条件

- 路由区分“候选技能参考”与“接受其默认业务口径”；普通部门统计不应静默继承 WBS 排除规则。
- LLM 在执行前把本轮意图转为受约束的查询计划，明确分组字段、指标、单位、行筛选和聚合后筛选；复用已有查询能力中的 HAVING，而非让展示层处理数学条件。
- 临时查询条件和永久修改技能分别处理；问“超过500k有哪些”不应被迫永久修改已保存技能。
- 若条件无法表达或没有被消费，拒绝完成声明或进入通用分析路径，不能直接执行旧计划后声称当前请求已完成。
- 验收同时覆盖“算术成立”和“请求条件落实”；回执保存实际采用的阈值、单位、运算阶段与命中部门。
- 回归至少覆盖：不指定技能的本次原话、明确指定技能并追加阈值、等于500边界、K与原金额单位转换、没有命中部门、全量与 WBS 排除口径隔离。
