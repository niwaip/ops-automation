## 4. 根因与责任区分

### A. 工程：自动补算不兼容本次 query 分组事实（已离线验证）

`registered_metric_completion.py:60–70` 虽将 query.metrics 转为 calculation 候选，但随后要求 `calculations.get(fact['id'])` 精确匹配，并要求事实本身带 `metric_id`。

本次计划度量 ID 为 `actual`；事实 ID 为 `actual__(('str', '营业收入'),)` 等带分组后缀的 ID，且事实没有 `metric_id`。因此全部在此处跳过，操作数 bank 为空。后续 `_leaf` 还要求 legacy 的 tables、table 及 unit 绑定，不能仅修 ID 就视为兼容。

离线探针使用原始回执、真实 `RegisteredMetricCompletion.complete`，仅将任务合约/状态固定为允许毛利率补算，并禁止源执行。结果为 **新增回执 0、源计算调用 0**，断言通过。这是当前代码的定点复现；原执行中也没有任何 `registered_derivation` 回执。

建议将 query 与 legacy 事实统一为明确的来源绑定，支持行式科目、分组事实 ID、操作数各自选行和单位一致性，再通过正常源计算引擎生成派生回执。不要用放宽门禁代替补算。

### B. 模型：错误计划与不完整修正（原始回执直接证明）

模型首次已取得足够数据，之后仍提交重复度量的无效计划。自我修正只恢复金额查询，没有执行毛利率计算。最终复核还称“未提取毛利数值”，与两份成功回执的毛利 53,443.25 相矛盾。

不能据此笼统判断主模型完全不会读表：它两次正确查询了金额，也修正了工具指出的度量冲突。失败集中在派生指标与修复闭环。

### C. 工程：复核输入与修复执行脱节

`analysis_task_state.py:536` 向复核员传递经过筛选的 facts、成功计划和所有历史 errors。当前业务目标是毛利率，修复所需的辅助毛利事实需要明确保留；过时错误也应标注是否已恢复。现有复核结论仍把历史 `invalid_analysis_plan` 描述为当前阻碍，并遗漏毛利已读取的事实。

`agent_loop.py` 的最终渲染分支调用 `AnalysisTurn.render`；`analysis_turn.py` 在最终状态不完整时记录 reject 并生成失败说明。这个阶段返回 `repair` 不会自动回到执行循环。因此最终复核中的“重新提取毛利”只是建议，没有产生补做工具调用。

历史 telemetry 记录了 7 次模型响应，全部为 `tool_calls`；只保留 4 次工具执行回执。没有逐轮完整 tool_call 原文和停止原因，**无法确定其余轮次与退出条件**，不将其直接定性为重复调用、工具被拦或轮次耗尽。

### D. 工程：模型代理连接故障增加耗时

18:53:29、18:53:52、18:54:03、18:54:09 出现 `aborted` 重试。18:54:05 日志明确记录上游域名 `chapter-defeat-favorites-extremely.trycloudflare.com` 收到的证书仅包含 `jsdelivr.net` / `*.jsdelivr.net`，随后尝试回退 `gemini-3.8-flash-high`。

这是传输/入口配置问题，不是财务数据缺失，也不是模型推理内容错误。日志只证明尝试回退，不能确认每段最终内容由哪个模型生成。未记录逐请求会话关联和完整回退结果，不能把全部失败归结于这一次证书错误。

### E. 失败提示过于泛化，但未发现后端原因空白

最终只说明毛利率来源“未核实”，没有告诉用户“金额已读取，尚未执行毛利÷收入”。后端完整回复实际已保存；用户展示为空的部分仍需浏览器/SSE 证据才能归因。

当前末尾回执成功，因此 `AnalysisTurn.render` 不再展示较早的工具错误，符合其抑制已恢复错误的实现。应展示尚未完成的派生计算步骤，而非重新展示过时错误或要求重传原件。
