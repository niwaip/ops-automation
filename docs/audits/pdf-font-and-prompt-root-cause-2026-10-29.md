# PDF 反复错误：字体、提示词与环境归因

## 结论

12:38 调用的字体失败不是“环境没有中文字体”，而是模型错误使用 FPDF API；平台仍注入旧 FPDF 执行指令、技能准入失败后退回通用脚本、排错成功被当作恢复，共同放大了模型错误。用户原始需求明确，无须改写或简化。

须区分用户提示词和平台提示词：前者没有要求 FPDF、斜体、下载字体或自行编写坐标排版；后者明确提到 bash、FPDF、常规字体路径和不断自愈重试。

## 字体错误逐项判定

| 错误 | 直接原因 | 环境责任 |
| --- | --- | --- |
| `set_font(FONT_PATH, size=14)` → `Undefined font: /opt/.../notosanssc-regular.otf` | `set_font` 使用已注册的字体族名，模型却传文件路径。应先 `add_font('NotoSC', '', path)`，再 `set_font('NotoSC', size=14)` | 字体文件存在；报错路径变小写是字体族查找归一化，不能据此判断 Linux 文件大小写或文件丢失 |
| `set_font('NotoSC', style='I')` → `Undefined font: notoscI` | 只注册常规样式 `''`，却请求未注册的斜体 `I` | 常规字体可正常使用。字体变体需要单独注册；原请求未要求斜体，是模型额外引入的需求 |
| 09:02 旧调用的 `Undefined font: nsB / nB` | 同样只注册常规字体，却切换粗体 `B` | 属于同类用法错误，不能通过重装常规字体解决 |
| `uni parameter is deprecated` | 使用过时参数，产生弃用警告 | 本轮警告后程序继续执行，不是致命异常 |

12:33 调用第一个 bash 已返回真实字体路径和 `fpdf2 ok`，这提供了当轮环境证据。随后常规字体注册也成功，报错推进到 `pdf.title(...)` 等其他位置，再次说明并非字体完全不能加载。

对当前运行环境做最小复现：FPDF2 2.8.8，字体文件 8,331,336 字节；正确注册并生成中文 PDF，输出 5,308 字节；随后故意传路径作字体族、请求未注册 I/B，均复现对应异常。未安装依赖、未下载或替换字体。结果见 `docs/artifacts/reviews/nature-handout-audit-20261029-1238/font-reproduction.json`。当前环境复现不能替代历史完整镜像快照，但与当轮日志一致。

## 平台提示词确有问题

`prompt_builder.py` 的 PDF 分支按消息中出现 pdf 即追加以下硬性要求：

- “你必须调用 bash 工具……执行 Python 脚本”；
- 必须用 `/opt/dsh/skills/pdf/assets/NotoSansSC-Regular.otf`；
- “初始化 FPDF 后……必须先显式调用 pdf.add_page()”；
- 脚本报错后自愈重试，“直到文件成功生成落盘”。

这段说明只给字体文件位置，缺少字体族名与路径的区别、Regular/Bold/Italic 注册契约及最小正确示例。它也没有按当轮工具列表切换：即使只有 render_pdf 而没有 bash，重建的提示词仍会包含必须 bash 的指令。

与此同时，PDF 技能与受控执行指令要求复用 WeasyPrint 模板、不编写 FPDF 脚本。两者在通用 prompt builder 中可同时出现，是可复现的指令冲突。当前托管 PDF 正文流程使用独立最小消息，因此成功路径绕开了该冲突；旧分支本身仍存在，前一轮“模板回退保护”不等于已清理全部旧提示词。

重建文本保存在 `reconstructed-pdf-prompt.txt`，明确标为当前源码重建，不冒充 12:33 原始网络请求的完整快照。历史事件已证明该轮准入失败并转通用 bash；因此旧指令的影响具有明确机制证据，但缺少当轮完整请求体，无法量化每条指令对模型选择的贡献。

## 为什么修复多轮仍出错

1. **模型没有稳定掌握库对象模型。** 后续 `pdf.title(...)` 与 FPDF 实例已有 `title=None` 属性冲突；`self.PH` 未定义；修成 `pdf.h` 又在实例方法中引用不存在的局部变量。正确方向是使用 `self.h`。这些是代码错误，不是字体环境或依赖故障。`dict object is not callable` 的具体中间脚本未完整保存，不能仅凭日志断言是哪一个属性被覆盖。
2. **任务退回了更难、更长的自由脚本。** 准入失败后模型要同时处理内容、坐标、字体、分页、图片和表格，失去固定生成器的能力约束。它在制作两页讲义之前先不断实现和修理 PDF 引擎。
3. **错误修复缺乏稳定基线。** 日志显示多个约 3,300 输出 token 的调用，交替生成脚本与诊断命令；修复一个错误后暴露另一个，期间没有先跑通最小中文页再逐项扩展。
4. **停止条件把排错成功当恢复。** 现有 repeated_execution_failure 只统计部分确定性错误，任何同工具成功都会重置计数。`help()`、打印属性等 bash 成功能清掉先前失败记录，即使从未生成 PDF；不同 TypeError/NameError 也不在该字体错误分类内。因此 7 次 bash 失败未能触发有效切换。
5. **上下文和无关指令增加负担。** 最后调用输入约 31,616 token，且混入不相关天气结果；这会增加推理与选择负担。没有 A/B 证据，不能据此断言模型能力、thinking 设置或上下文长度是唯一根因。

## 修复优先级

1. 清理 prompt builder 中“PDF 一律 bash/FPDF”的旧指令，按实际工具生成执行说明，消除与受控模板冲突。
2. 将字体文件、家族及可用样式作为确定性能力契约；需要自定义 FPDF 时提供验证过的最小示例，不让模型猜字体名与变体。
3. 只以目标生成器成功或交付物验证成功重置文档失败状态；只读诊断成功不代表产物恢复。对不同脚本异常累计失败预算并及时切换方案。
4. 保留原生模板负责字体与布局，模型负责正文的职责边界。已验证这条路径可以完成原始需求，不能据本轮错误直接推导“必须换模型”。

本次补充工作只做归因、环境复现与证据归档，未修改业务代码；上列旧提示词和失败计数改进是仍待落实的事项。
