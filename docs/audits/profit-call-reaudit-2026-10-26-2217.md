## 5. 根因一：输入附件被当成输出交付需求（P1，新回归）

实际传给 dsh 的文本包含：

```text
【当前轮次用户上传附件】: AI能力测试_财务报表.xlsx（这是用户本轮刚上传的新文件，为本次指令的主要处理对象）
用户指令：解释下半年盈利能力变化。
```

新增代码在 `last_user_prompt` 全文中匹配 `artifact_terms=(".pdf", ".docx", ".xlsx", ...)`。该变量来自 runner 传入的包装 prompt，而非只包含用户需求的部分。因此，即使 `expected_deliverables=[]`、`is_generate_intent=false`，文件名也使 has_visual_or_deliverable 为 true。

离线直接执行当前真实赋值表达式，得到：包装文本 true；仅用户指令 false；触发词为 `.xlsx`。

这一 flag 同时影响：

1. 分析工具裁剪时合并更广的工具集合，而不是只保留分析能力。
2. 注入“当前任务既要求核算又要求图表/页面”的指引，尽管用户只要求解释。
3. 无工具响应时跳过 `spreadsheet_analysis_required and not has_visual_or_deliverable` 的专用核验。
4. 最终跳过 `AnalysisTurn.render()`，进入通用 `_finalize_agent_text()`。

这解释了为何本次有成功取数和复核调用，却没有专用分析门禁 accept/reject，最后原始模型正文直接保存。

**修复建议：** 交付需求以已有的 `output_mode/artifact_types/expected_deliverables` 为依据，附件格式只表明输入类型。若保留文本补充识别，必须先提取用户指令并要求明确生成动作；不能仅因出现扩展名就切换交付模式。更关键的是，数值核验应独立于文本或图表呈现方式，真实可视化任务也不能跳过计算正确性检查。

## 6. 根因二：把“有数字”误当成“指标已核算”（P1，已有漏洞被暴露）

本次复用的契约缓存 `2aaafb7d…` 于 22:03:54 生成，metrics 为：

```json
[
  {"name":"盈利能力变化","expected_type":"number","semantic_id":null},
  {"name":"净利润","expected_type":"number","semantic_id":"finance.net_profit"}
]
```

“盈利能力变化”是分析目标，不是可直接求和的列；也没有得到定义、单位或明确公式。通用检查通过 `_extract_metric_value_from_reply()` 在同一行查找指标词和任意数字，不比较其与工具事实或确定性派生结果的一致性。

对实际最终正文执行该函数，返回有效数值 **`2`**。原因是正文有标题：

```text
### 2. 盈利能力变化计算
```

这是与模型能力无关的确定性漏洞。单纯要求模型把指标名写出来，会诱导其将复杂解释任务包装成一个自定义数值指标；本次最终回答正是把整项分析收缩为“盈利能力变化这一指标等于净利润增长率”。

**修复建议：**

- 分离抽象目标、业务指标、派生指标与来源字段。派生指标必须有类型、公式、期间和来源依赖。
- 完成状态依据结构化事实与派生计算，不从最终自由文本寻找数字作为通过条件。
- 标题序号、月份范围、公式编号和历史答案不能成为事实证据。仅过滤 Markdown 标题还不够，因为正文中的无关数字也能误匹配。
- 通用 finalizer 与专用分析 finalizer 共用同一数值验收结果，不维护强弱两套完成判断。

代码：[analysis_validation.py](/Users/chain/Documents/MyProject/ops-automation/apps/backend/runtimes/personal-sandbox-runner/src/dsh_modules/analysis_validation.py:41)，以及 [final_answer.py](/Users/chain/Documents/MyProject/ops-automation/apps/backend/runtimes/personal-sandbox-runner/src/dsh_modules/final_answer.py:338)。
