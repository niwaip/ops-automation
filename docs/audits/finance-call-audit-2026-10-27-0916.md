## 4. 09:16 原调用逐步还原

1. **原生 round 0：计划真实错误。** 四个不同业务指标都对同一列 `2026实际` 做全范围 sum，既不按项目分组也不分别筛选科目，将得到相同的混加结果。`query_contract.py:303` 正确拒绝“度量定义冲突”。同一计划还把“毛利率”表达式写成 `ref=revenue`，并引用未定义的 `operating_margin_calc`；程序在更早的查询校验处终止，未继续验收这些表达式。
2. **原生 round 1：改成直接单元格读取，但 where 为 `{"and":[]}`。** 编译器拒绝空逻辑条件：`and 组合操作需要 1 到 16 个子条件列表`。本次两个错误均已离线逐字复现，不能称为规则误报。
3. **两次原生失败后，程序自动开放 bash。** `agent_loop.py:526–537` 将聚合、等式、字段验证和比较工具的错误都纳入同一计数，并注入“请立即编写 Python 脚本”指引。模型转用 Python 是受程序指引影响，不能全部归咎模型擅自绕路。
4. **Python 两次异常。** 直接 `openpyxl(data_only=True)` 读取利润表得到 None；月度经营收入和部分利润有缓存，但所得税、净利润缓存缺失，格式化 None 报 `TypeError`。
5. **末次 Python 成功。** 输出税率 0.25、收入 124,020.00、毛利率 43.09%、营业利润 21,209.40、净利润 16,038.30，以及补充计算结果。该回执状态 success，但 data 是 stdout 字符串，provenance 只有 tool=bash、round=5，没有来源哈希、结构化事实、覆盖范围和 evidence_id。
6. **最终核验仍失败。** `analysis_task_state.py:93` 只收取成功且 data.kind 为 spreadsheet_analysis 的回执；本次符合条件的回执数为 0。`AnalysisTurn.render()` 同样不将成功 bash 作为可交付分析证据，最终生成用户所见的未完成提示。

09:20 重试的两个原生错误分别是 `tables必须是JSON数组` 和 `group_by 必须是列表`。其后脚本曾输出所有指标为零，后续得到收入、毛利率和营业利润，却仍将净利润 None 汇总为 0。进程成功退出不等于业务结果正确，保留证据核验是必要的。

## 5. 确定性工程缺陷与模型责任

### P1：退避执行与最终验收契约不一致

`agent_loop.py:531` 允许从原生工具退避到 bash；`analysis_task_state.py:93` 和 `analysis_turn.py:225` 却只认原生分析证据。用户因此花费多轮计算成本，仍无法完成。

应优先让错误计划回到已验证的声明式协议修复，或建设能独立验证来源、公式、范围与数值的脚本结果适配器。不能靠把任意 stdout 包装成 success 或关闭门禁解决。

### P1：复核器看不到失败计划和后续成功脚本，形成陈旧诊断

`analysis_task_state.py:596–600` 只向复核器传成功原生 plans/provenance、事实和错误 message。失败回执已有 requested_plan，却没被传入；成功 bash 的 stdout 也没被传入。复核器因此看到 `plans=[]`，错误推论“没有真实执行，所以计划错误是误报”。

第二次 Python 失败的 error message 含 stdout，复核器能由此看到三项结果和净利润 None。最后一次 Python 成功后，反而因为 success 不在 errors 中，其完整四项结果未进入复核上下文。

离线对原始回执分别执行“末次成功前”和“末次成功后”的状态函数，捕获的**全部复核调用参数完全相同**。缓存键覆盖这些参数，因此同一进程内该成功结果也不会使先前复核缓存失效。最终日志中仍保留“净利润显示为None”的旧诊断，与末次 stdout 冲突。

修复时区分失败尝试、成功原生事实、成功外部执行；将 requested_plan、结构化错误位置、来源信息、工具结果摘要/哈希和执行状态纳入复核上下文及缓存版本。脚本输出可用于诊断，仍须独立校验后才能进入已验证事实池。

### P2：复核模型给出错误诊断与无效工具建议

首个复核把真实“同列混加”判为误报，混淆了利润表的行标签与物理列。重试的复核又建议 `columns`、`operations` 等工具未定义的顶层参数，并建议毛利率 mean/avg，缺少年度加权口径依据。

模型承担计划和复核语义错误责任；工程承担未提供实际失败计划、未验证修复参数以及未使修复收敛的责任。正确路径是限定复核输出为可由同一编译器校验的补丁；语法错误先反馈精确位置和合法结构，不让第二个模型重猜完整工具 API。

### P2：终态提示将“没有认可证据”误写为“尚未执行”

`report_presentation.py:350–363` 根据 missing_metrics/source_column_exists 直接生成“尚未执行聚合”，无法表达“原生计划失败，脚本计算已输出，但证据未接入”。`analysis_turn.py:214` 又因为最后一条回执 success 而隐藏先前执行错误，最终用户只看到重试建议，无法知道实际阻碍。

此外，“收入差异、收入预算、收入实际”和“营业利润率”只是跨表表头/别名候选，不代表已经绑定本次指标的正确物理来源。提示不应把这些候选统一称为对应列，也不应暗示只有 sum 聚合才能完成直接取数。

应分别报告计划校验失败、公式缓存缺失、已执行但证据未核验、任务覆盖不足。系统能自行修复的执行缺项应在本轮修复，不能把“再试一次”作为常规闭环。
