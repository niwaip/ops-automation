# 22:44 月份偏差调用审计

## 1. 结论

**存在可复现的工程误拦，不能解释为表头或 Sheet 写错，也不能解释为模型没有计算能力。** 本轮已经成功比较全部 12 个月，但契约将派生结果“偏差”与来源指标“收入、净利润”平铺，最终门禁要求物理来源表头包含“偏差”，拒绝了合法结果。用户看到的“已达成指标：无”和“请根据真实表头确认”都不准确。

本轮的实际失败链是：**不合适的主表预检上下文 → 含混的模型契约被固化缓存 → 硬性排序约束 → 合法工具结果 → 派生指标被要求匹配来源表头 → 整体拒绝。**

定性为**工程为主、模型语义输出错误参与的复合问题**。模型裁判将派生量平铺、把含混问题锁定为 cross_metric/signed；程序没有区分显式要求、推断假设、原始操作数和派生结果，又把这些推断当成不可修改的用户要求。后续模型还生成了空列、重复标签等无效参数，应保留对应结构校验，但这些错误不能抹掉已经成功的核算。

**来源校验需要保留，但职责边界需要调整。** 本次没有证据表明 `SemanticFilterJudge` 因年份、来源标题或 Sheet 名不一致拒绝了结果；直接拒绝来自 `comparison_evidence.py` 的比较计划/结论门禁。普通分析的来源裁判不能与该比较门禁混为同一原因。

## 5. 根因与代码位置

### 5.1 预检上下文与任务契约没有区分来源角色

`analysis_contract.py:_resolve_available_headers` 只取预检的主表 headers，未携带全部候选表、公式关系和多区域结构。原请求的预检主表实际是**管理驾驶舱**，表头为 `核心指标、数值、月份、收入、净利润`，不是最终执行的月度经营表。

以原请求和这些表头计算 v4 缓存键，精确命中 `5e4071c8…c2a613`。缓存内容为 `metrics=[收入,净利润,偏差]`、`comparison_basis=cross_metric`、`ranking=signed`。缓存修改时间为当日 21:58:35；它不是本次新生成。这里是按当前相同运行源码和输入重建缓存选择，原遥测未直接记录契约哈希。

其他表头上下文对应的同句请求缓存已有不同的 metrics/ranking。不能把它描述为一次调用内部随机改判：同一进程有表头缓存；可以确认的是**契约随表头上下文而变化，而且没有区分推断与用户明确要求**。

### 5.2 派生指标被强制要求出现在物理表头

[`comparison_evidence.py:150`](../../apps/backend/runtimes/personal-sandbox-runner/src/dsh_modules/comparison_evidence.py#L150) 对 contract.metrics 逐一要求匹配 left_headers/right_headers。原件实际表头是“营业收入”和“净利润”，所以“偏差”永远匹配不到，纵使已经记录差额、公式、源坐标和完整范围。

`comparison_plan_error` 对该成功回执返回 None，而 `compile_comparison_response` 最终精确返回原错误：“回复的指标、极值分组或偏差数值与本轮来源证据不一致：偏差”。**这是派生表达式覆盖建模缺失，不是数字或月份算错。**

比较回复由 `comparison_delivery.py` / `report_presentation.py` 按回执生成，然后又通过上述文字匹配验收。因此这里被拒绝的实际是程序编译出来的答案，不能仅凭错误中“回复不一致”归责为模型编造答案。7 次响应的 rawChars 都为 0，finishReason 都为 tool_calls。

### 5.3 将模型推断描述成用户明确约束

[`comparison_evidence.py:39`](../../apps/backend/runtimes/personal-sandbox-runner/src/dsh_modules/comparison_evidence.py#L39) 严格比较排序枚举；43 行又把 comparison_basis 冲突描述为“改变了用户明确指定的基准”。但原句没有明确说 signed，也没有明确说跨指标相减，都是裁判推断。

这不是应当全局删除排序校验的理由。应当记录用户显式约束与可修正的推断假设；含混的解释由 LLM 结合真实来源消歧，再把确定的计划交给程序执行。

### 5.4 后续指定预算表仍失败，证实不是缺 Sheet

同一会话 22:47 的追问明确指定“预算对比sheet”。该表存在，实际列为收入预算 B、收入实际 C、收入差异 D、利润预算 E、利润实际 F、利润差异 G。工具也实际读到了这些表头。

对应缓存 `c515bbb4…47ec4a` 输出 `metrics=[收入差异,利润差异]`，却仍给 `comparison_basis=cross_metric`。[`analysis_contract.py:121`](../../apps/backend/runtimes/personal-sandbox-runner/src/dsh_modules/analysis_contract.py#L121) 又用任意正则命中领域词表：`收入差异` 被其中“收入”命中并归为“营业收入”，`利润差异` 则保留为字面指标。

于是收入实际/预算的列对能关联营业收入，净利润实际/预算的列对却无法关联“利润差异”，产生“未能由来源表头确认”的拒绝。把 basis 改为 custom 又违反缓存的 cross_metric。这是契约与来源绑定互相矛盾，不能要求用户继续补列坐标来补救。

离线使用同源、同范围的两组实际−预算列对，并明确按绝对差额取极值，得到收入 12 月 +1,870 千元、净利润 7 月 −445.6875 千元。该结果仅是对后续预算口径的反事实复核，不是原调用已成功交付的内容。

### 5.5 来源裁判不是本次直接拒绝者

本例契约 period=null；列比较交付路径直接使用物理表头、哈希、范围、分组与数值检查。离线重放禁止调用 `SemanticFilterJudge` 后仍完整复现同一失败。

比较路径目前也没有利用普通分析中的语义来源裁判纠正这一契约冲突。不能得出“把来源裁判的严格提示词删掉就能修好”的结论。现有来源裁判已经有 true/false/None 三态和同义词要求；更关键的是比较流程如何消费语义绑定、区分冲突与未识别，并将可恢复问题送回模型修复。

## 7. 建议的调整边界

1. **P1：将业务目标、来源操作数、派生表达式分开。** 比较的覆盖判定应是“收入与净利润两个源绑定 + 已执行相减表达式 + 12 个月极值”，不要求原件存在“偏差”列。已有差异列也可作为直接取值，显式保留它的来源角色。
2. **P1：让 LLM 做来源语义绑定与含混解释，程序检查绑定后的事实。** LLM 识别 Sheet/表头同义词、科目行、多级表头和公式关系，给出真实 Sheet、坐标与表达式；执行器检查存在性、数值、单位、期间、覆盖和结果。名称不同或尚未识别应进入重新读取/重绑定，不能直接等同于来源错误。
3. **P1：区分用户明确约束与推断假设。** Sheet=预算对比是明确范围；cross_metric/signed 在本例只是推断。结合该表预算/实际结构重新确定口径。若存在两种会改变答案的合理解释，给出明确假设或询问业务含义，避免让用户提供机器列坐标。
4. **P1：取消子串命中就吞掉派生语义的标准化。** `收入差异`不能仅因含有“收入”就归成原始营业收入；领域 ID 映射需保留预算、实际、差额、比率等角色。绑定过程可用 LLM，最终 ID 与来源表达式应固定在本轮计划中并记录证据。
5. **P2：比较验收优先使用结构化事实。** 程序已经生成的答案应直接从经过验证的结构化结果渲染；不要再靠同一组表头正则验证派生量。模型额外叙述中的数字仍需绑定事实，错误数值不能放行。
6. **P2：将门禁失败变成具体修复反馈。** 返回缺哪个绑定、哪条表达式、哪个期间或范围冲突；允许一次有边界的语义复核或重规划。不要将所有失败都描述成“真实表头不对”，也不要把已经核算的指标全部写成“无”。
7. **保留硬校验：** 文件哈希、真实源存在性、公式重算、单位换算、明确期间与业务过滤、全量月份覆盖、并列极值、数值一致性、合法参数。不存在的 Sheet 不应凭相似度静默选错；可以由 LLM 从工具返回的真实工作表列表重新选择。

本轮仅新增审计报告、封存材料和离线探针，未修改业务代码、缓存、原附件或用户会话，未重启/部署服务，未向外部模型发送附件数据。工作区原有大量未提交改动保持原状。
