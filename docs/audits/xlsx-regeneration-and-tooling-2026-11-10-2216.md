## 结论

此次无法正常重新生成的主因是工程路由遗漏。22:15 成功使用原生 OOXML 固定翻译流程；22:16 的语义复核已正确判断为 followup，且一度恢复了“保持格式不变、翻译成中文、Excel”的要求，但通用工作簿更新分支清除了技能身份，固定翻译入口又只检查当前句子的“翻译”动词和目标语言，最终进入通用 ReAct 循环。

## 修复范围与验证

新增 `xlsx_translation_routing.py` 承担纯路由解析，避免把上下文恢复堆入执行器。

- 本轮必须是经过复核的执行/文件交付 followup，且只有一个 XLSX 输入。
- 简短重试恢复最近一项实际用户任务；不跨过更近的其他任务寻找旧翻译要求。
- 继续执行此前完整请求的范围检查。部分表、保留表名、邮件发送、多文件和明确调用其他技能均不被整本翻译入口接管。
- 接受复核模型的不同合法引用形式：只引用“重新生成”、引用原任务、或同时引用两者。实际用户原话是恢复任务的依据，不依赖复核模型是否重复抄写全部旧要求。
- 通用准入的 `skill_id=None` 仅在上述受控重试条件下进入运行时工作流，不继承未经准入的技能正文。
- 每次重新生成仍提取原件、构建新候选、执行完整性验收，然后原子发布；失败不以旧文件冒充本轮交付。

18 项翻译相关测试和 1 项既有 OOXML 集成测试通过，新增回归涵盖本次真实意图结构、范围继承、其他技能选择，以及缓存复用情况下真实重建并验收 ZIP。实际 Broker 验证确认未进入自由工具循环。

两次中间修复试验分别暴露“同时引用重试句”和“仅引用重试句”这两种合法复核形式，均中止并保留日志，最终版本覆盖两者。新 Python 进程从现有源码挂载加载修复；没有修改容器启动配置或重启后端服务。

## 当前是否使用 OOXML

是。当前固定流程使用项目自己的 Python ZIP/XML 引擎 `ooxml_xlsx_translate.py`，对原包里的文本进行替换，保留非目标部件、样式和媒体，并同步公式中的工作表引用和文本判定常量。图形文字按原 XML 节点替换，避免整体重新序列化图形。

这是直接处理 OOXML 格式；没有使用微软的 .NET Open XML SDK。两者不是同一概念。当前默认也不通过 LibreOffice 重写交付工作簿。

保留原数值缓存，设置 Excel 打开时重新计算；尚未证明该文件经过原生 Excel 计算和全表视觉验收。QA 中 `visual_reviewed=false`、`semantic_reviewed=false` 保持如实记录。此前已有关键页面视觉抽查，不能推广为逐页、逐句全面验收。嵌入图片里的日文仍保持原样。

## 选型建议与剩余缺口

对这份“保持复杂 Excel 格式不变”的文件，继续使用原包局部修改和固定验收流程更有现有证据支持；不建议仅为换 skill 而回退到 openpyxl/LibreOffice 全包重写。但当前实现尚不能称为业界最优的完整翻译产品。

后续优先补强：整句上下文与富文本段之间的对齐、统一术语表、按语境区分重复字符串、译文缓存策略版本、真实全文重译的独立入口，以及漏译/长文本溢出/语义抽查。用户已确认图片不需要翻译，图片保留原样，不将 OCR 列为本任务缺口。数值公式计算仍应交给原生 Excel 验证。

若评估 Okapi，建议先做离线提取/回填对照，不更换现有交付链路：使用同一原件和相同译文字典，比对 120 个部件、图形坐标与媒体、富文本、标准和扩展规则、公式引用及文本常量，再做视觉抽查。通过后再比较同模型、同输入的冷启动时间、请求数、tokens、术语一致性和人工错误率。当前尚未完成该基准，不能声称 Okapi 一定更快或更保真。

## 用户补充规则：仅同会话复用

用户确认“同一个会话可以复用结果，不同会话不要复用结果，图片不需要翻译”后，已将缓存改为 `xlsx-cache/3`，绑定会话 ID、原件 SHA256、语言和模型。不同会话不会读取相同原件的其他会话译文或直接使用旧成品；缺失会话身份时使用本次运行作用域，不能回退到用户工作区全局缓存。

底层 CLI 文本检查点同步升级 `xlsx-text-cache/3`，绑定 `DSH_SESSION_ID`、输入文本哈希、语言和模型。无会话标识不读取旧检查点，旧版没有会话绑定的缓存不自动迁移。发布与完整性验收仍每轮执行。

仅对本次同一实际会话，从其最新成功回执所指向的已验收任务目录迁移了 2,544 条检查点，核对原件哈希、发布状态和质量回执一致；没有从共享全局缓存或其他会话导入。迁移证据为 `session-cache-migration.json`。
