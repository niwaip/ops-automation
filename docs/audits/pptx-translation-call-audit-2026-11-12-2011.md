## 3. 确认的质量问题

### P1：第 1 页主体架构图整图漏译

第 1 页只有两个非空原生文本段落参与翻译，分别是标题和副标题。主要架构内容实际存于 `ppt/media/image12.png`，通过该页 `rId2` 图片关系引用。

原件与成品中此图片字节完全相同，SHA256 为 `6ef724f8db06f101c7a9f903802a56da5183846be5778855a86378969dc8ee08`。直接查看嵌入图片及整页预览，仍能读到“访问入口层”“企业用户”“PC 浏览器”“移动端”“管理员”“数据服务区”“运维与安全区”“统一入口”“弹性扩展”“数据安全”等大量中文。

这不是个别品牌或技术缩写保留，而是主体业务标签和说明没有处理。**第 1 页标题已日文化，主体图仍为中文，直接否定“全页全要素覆盖”的完成声明。** 图片中的文字也仍不可作为原生 PowerPoint 文本编辑；这是原件已有属性，本轮没有改善。

### P2：字号和粗体层级发生了未披露变化

独立比较每个段落首个 run 的 `sz` 属性，共确认 **19 处显式字号缩小**：第 2 页 18 处，第 3 页 1 处。例如：

| 位置 | 原字号 → 成品字号 |
| --- | --- |
| 第 2 页标题 | 27 → 23.22 pt |
| 第 2 页“安全边界” | 13.5 → 10.8 pt |
| 第 2 页“浏览器・移动端” | 10.8 → 8.64 pt |
| 第 2 页“向量检索・知识库” | 8.9 → 8 pt |
| 第 3 页“外部攻撃防御” | 9.19 → 8 pt |

另有 **21 个文本框的 AutoFit 配置发生变化**。缩字号可以是合理的排版手段，但与回执“保留……字体大小设置”不一致，也不能据此推导已经验证可读性。

第 8 页“スタンダード版”和“カスタマイズ版”两段，原件只有版本名称与冒号加粗，后面的长说明是普通字重；成品将完整段落放进第一个 `b=1` 的 run，后续 run 文本清空，导致**整段说明全部加粗**。这两段文字内容本身没有变化，仍被回填破坏了原有强调层级。XML 与预览均支持这一结论。

### P2：已是日文的部署区域标签被改成“设置区域”

第 3 页：`Alibaba Cloud 配置領域` → `Alibaba Cloud 設定領域`。

此标签位于包围 WAF、OneAI 和模型服务的部署边界上；结合第 2 页的“阿里云部署区”，这里表达的是配置/部署区域。改成 `設定領域` 容易被理解为设置区域，改变了图示含义。建议统一为 `Alibaba Cloud デプロイ領域` 等明确表达，并与第 2 页保持一致。

另有较轻的术语问题：第 2 页“访问端”译为 `アクセスエンド`，不如第 3 页已有的 `アクセス元` 自然；同一文稿并用 `アリババクラウド` / `Alibaba Cloud`、`AI Agent` / `AIエージェント`，可按企业术语表统一。这些属于流畅度和一致性问题，不据此认定全文语义失败。

### 排版风险：替代字体预览中第 2 页出现重叠

补做的 LibreOffice 预览中，第 2 页左侧“ユーザー／クライアント”被挤为三行并与显示器图标重叠；上方请求/响应标签与“OneAI プラットフォーム”标题也贴合或重叠。第 7 页 `AIエージェント／自動化` 出现孤立换行。

这些是已经观察到的预览问题，但渲染环境以 Noto Sans CJK 替代 Meiryo、Meiryo UI、Yu Gothic，**不能直接断言原生 PowerPoint/WPS 在原字体下完全相同**。原件在替代字体下也有部分换行问题。确定事实是原执行没有保存视觉验收记录，而字号和 AutoFit 估算未能在此次预览中避免全部重叠。

## 5. 为什么质量门禁仍通过

使用实际原件和成品、零模型调用重新执行 `validate_pptx_translation_delivery()`，仍返回 `ok=true`、`issues=[]`、`warnings=[]`，与本轮回执一致。

当前代码的关键边界如下，路径均相对 `apps/backend/runtimes/personal-sandbox-runner/`：

1. `skills/pptx/scripts/ooxml_translate.py:36` 只抽取 slide XML 中带 `a:r` 的 `a:p`；不会 OCR 图片。当前文件的主要漏译内容从未进入翻译字典。
2. `src/dsh_modules/pptx_workflow.py:204` 的扫描同样只看原生段落，`:315` 通过少量简体特征字检测残留。第 1 页仅两段原生文字，图片中文不在检测范围；“残留简体中文 0”只在这个范围内成立。
3. `pptx_workflow.py:332` 检查的是字号/颜色属性**数量是否损失一半以上**，没有逐项比较字号值或粗体范围。属性计数从 305/289 变为 310/294，仍可通过，即使真实字号变小或粗体层级已经丢失。
4. `ooxml_translate.py:734` 把整段写入第一个 run、清空其余 run。第 8 页首 run 是粗体，于是后续普通文本继承了粗体。这是确定的回填实现问题，不需要模型犯错即可发生。
5. `ooxml_translate.py:119` 以假名/短字符规则识别可透传文本。没有假名的日文标签仍可能被送去重译；模型输入是去重后的短文本字典，没有页面区域和邻近节点关系。该机制会增加术语漂移机会，但无法仅凭一轮记录量化其贡献。
6. `pptx_workflow.py:428` 附近固定输出“全量翻译”“全页全要素”“字体大小保留”的模板。模板没有根据 OCR 覆盖、字号变化、语义复核或视觉验收状态调整措辞。

证据顶层 `verified=false`，但指标的 `finishReason=verified_pptx_translation`、回执 `quality.ok=true`。这些状态口径不一致，后两者实际证明的是当前启发式门禁通过，不能视为语义与视觉均已验证。

图谱已用于代码入口发现；索引未覆盖新增的 PPTX 工作流符号，具体定位以当前源码、挂载脚本及运行证据交叉核对。审计时共享技能目录脚本与仓库脚本哈希一致，已保存当前代码快照；未保存执行前完整源码快照，不能把审计时源码无条件等同于执行前版本。

## 7. 修复建议与验收目标

1. **先补第 1 页图片文字。** 识别主体图中文字后，在保留架构连接关系的前提下本地化，或获取可编辑原图；若无法处理，应明确披露图片文字未翻译并禁止输出“全要素完成”。官方 Logo、品牌与技术缩写可按术语策略保留。
2. **回填保留 run 样式。** 未改文字应优先保留原 XML；混合格式段落需要保留版本名称与正文的强调边界。用第 8 页两段说明验证“只让前缀加粗”，不能只验最终字符串相同。
3. **分开报告格式变化和验收状态。** 记录每处字号、AutoFit 与字体的实际变化；将原生文本覆盖、图片文本覆盖、语义复核、视觉验收分别表达。允许缩字也要披露，完成回执以实际检查结果为准。
4. **翻译保留最小页面语境。** 给区域标签附所属页、相邻标题和部署边界信息；已是日文的词不应无条件重译。针对 `配置領域 → 設定領域`、`アクセス元` 等做术语一致性核对，避免硬编码整份文档句子。
5. **对密集页做视觉验收。** 第 2、3、8 页优先检查图标与文本重叠、区域标题、尾字换行和正文截断；使用目标字体或原生 PowerPoint/WPS 验证，替代字体预览只作为风险线索。
6. **补齐执行可观测性。** 附件翻译意图应在准入前形成一致的 artifact 契约；记录翻译与补译的批次、调用 usage 和必要映射证据，避免固定流水线隐藏子调用、又宣称 token 完整。

本次建议没有实施为代码修复，也没有生成替换译稿。
