## 4. 根因与责任分层

### 4.1 工程：默认关闭的引擎被作为正常翻译入口使用

CLI第35行要求 `DSH_PDF_TRANSLATION_ENGINE=layout-html-v1`，否则在调用pipeline之前直接抛出 `engine_not_enabled`。

本轮两条独立工具回执均包含该错误。只读核查目标沙箱容器配置，未发现该环境变量；容器从17:15:41启动至核查时仍为同一运行实例。当前镜像仍是原沙箱镜像，未启用生产灰度，与之前实施记录一致。

因此当前用户重试不会使新版翻译功能自动可用。正式启用应建立在真实样本验收之后；不得让模型自行设置环境变量绕过灰度。

### 4.2 工程：已失败的翻译尝试没有成为结构化job证据

第2次auto回执是通用 `shell_command_failed`，data为null，不是带manifest_path的 `pdf_translation` 回执。最后门禁进入 `_pdf_translation_jobs` 为空的分支；工作区也未发现本轮job目录。这表明本轮auto没有形成有效的父进程翻译桥接登记。

**登记缺失已确认，其精确触发语法未能确认。** 当前metrics将命令截断为120字符，auto命令尾部不在已保存证据中。unpack本来就不属于当前桥接器识别的auto/pack发布尝试，不能单独解释auto为何失配。

只读运行现有命令识别函数发现：标准auto、末尾 `2>&1` 和前导注释均可识别。因此不能把这次问题直接归因为“加了stderr重定向/注释”。其他复合shell写法、当时源码版本或上下文差异仍需完整命令证据排除。

CLI的灰度检查发生在pipeline建立manifest之前；一旦父桥没有登记，早期失败就只留下通用shell错误。这个组合使最终门禁只能给出“manifest缺失”，没有保留最直接的未启用状态。

### 4.3 模型：收到不可用状态后继续寻找历史替代成果

两次错误后，模型执行 `find /workspace -name "*.pdf"`，检查4页、9页、10页的旧版本，并把字符数量当作“文本覆盖质量”的参考。字符数不能证明逐段译文完整，页数不同也不直接等于遗漏或完整。

第10次命令预览明确包含：

```bash
cp /workspace/PDFMathTranslate_CN.pdf /workspace/2507.03009v4_中文版.pdf
```

复制源和目标的SHA-256均为：

```text

```

复制源611,876字节、10页，工具回执列出的时间为13:54；目标只是本轮产生了新修改时间。旧产物没有本轮来源绑定和当前候选的全页视觉回执，不能作为重新翻译成果。

### 4.4 门禁：拒绝正确，提示覆盖与文件隔离仍有缺口

最终 `check_pdf` 的 `valid=true` 仅表示结构检查通过。其结果明确写着 `visual_review=required`；本轮没有 `pdf_page_review`、`pdf_layout_analysis` 或 `pdf_translation` 模型调用，也没有全页PASS证据。不能把PNG生成或目录列举当作视觉审阅。

翻译门禁要求当前run的来源/译文证明，因此正确拒绝了复制的旧PDF。但最终提示把最早的 `engine_not_enabled` 覆盖成 `translation_manifest_missing`，使用户误以为已生成有效译文、只是缺回执。

此外，无job分支只清空outbound，没有将这个复制文件隔离。核查时目标文件仍在工作区；它未通过本轮验收，不能在下次重试中被误当作已批准结果。与有job分支的隔离策略需要统一。

## 6. 修复顺序

1. **能力状态前置且可终止**：保持调用结构，在已有工具执行/回执处理中将 `engine_not_enabled` 标为不可在本轮修复的状态；模型应停止，不继续搜索和复制历史文件。
2. **失败证据可追踪**：CLI早期失败也应产生与父run绑定的结构化尝试记录；桥接器对语义等价命令的识别范围要有明确边界。缺失时保留真实错误，不仅显示manifest缺失。
3. **隔离统一**：无manifest分支也隔离本轮未经认可的目标，保留输入和旧合格文件，不通过放宽门禁补救。
4. **启用闭环**：在获准模型与隔离沙箱完成原7页论文真实验收，再把开关配置到实际生产DSH环境；当前代码存在不等于用户翻译能力已经上线。
5. **回归覆盖真实失败链**：补测“引擎关闭→auto失败→复合命令/缺job→复制旧PDF→最终拒绝”的整轮路径，验证一次失败即结束、明确提示、无外发及无公开新草稿。
