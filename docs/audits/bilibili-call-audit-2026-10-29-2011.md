# Bilibili 单页 PDF：20:11 调用审计

## 1. 结论

**失败属于工程缺陷与模型参数错误叠加，最后的阻断直接来自上一轮修复新加的图标限制。**

1. 前两次 render_pdf 分别传了 3 项和 2 项 pages，不符合一页要求；其中都有一个独立 `_END_` 伪页面。
2. 第三次已改为 1 项，输入校验通过，但标题含 📰，新 symbols.py 不支持 U+1F4F0，直接抛错，尚未生成候选 PDF。
3. 止损器将输入页数错误和不支持图标都归为 pdf_render_failed，累计到 3 次立即终止。不是同一个错误原样重复三遍；模型已经修复页数，但没有获得修复新错误的下一轮。
4. 最终回复退回通用交付物路径，丢失“具体因哪个图标失败”的信息，只显示“未落盘”和“错误上限”。用户不缺需求，也没有证据需要用户补充条件。

本轮确实加载了新修复：已改用 render_pdf，没有 bash 排版，且实际报出新 symbols.py 的错误。不能归因于没重启、旧代码未生效。上轮修改成功防止缺字 PDF 被误交付，但**用有限图标列表拒绝未知图符的策略不够稳健**，将普通装饰变成了整份文件生成的硬依赖。这是本次需要承担的工程回归。

本次仅审计、归档和只读复现，没有修改业务代码、重启业务服务或重新生成用户 PDF。

## 5. 工程根因

### E1：未知图标策略使普通文档不可生成

symbols.py:49–51 对所有不在小型 SVG 映射表中的 U+1F000～U+1FAFF 字符直接抛 ValueError。上次测试覆盖已映射图标，并且专门断言“未知图标必须失败”，这能证明不悄悄产生缺字方框，却不能证明任意合理新稿可成功生成。

这次真实第三稿不只缺 📰。只读复现确认：仅去掉 📰，下一处就变为 🏀（U+1F3C0）失败。稿中还包含 🌎、💰、📍、🚗、🇪🇸 等未覆盖图符，共 8 个未覆盖码点（旗帜由两个码点组成）。因此仅补一个报纸图标仍不能闭环。

应区分装饰图标与承载数据的符号。装饰可使用确定性安全替代或通用本地矢量资源；排名、趋势等语义须保留为数字/文字。明确要求特定图形、确实无替代资源时才应报具体能力问题。不要依赖不断追加本轮出现的 emoji 名单，也不要恢复带缺字的 PDF 交付。

### E2：联网 PDF 漏掉模型 schema 页数绑定

agent_loop.py 中 managed_pdf 的判定排除 web_search。configure_pdf_tools 只在 managed_pdf=true 时运行，因此“联网检索 + 原生 PDF”已经选中受控生成器，却没有把单页要求绑定为工具 schema 的 minItems=maxItems=1。

只读检查真实工具选择分支：包含 web_search、fetch_page、render_pdf、inspect_pdf_page、read_file；pages schema 仍为 minItems=1、maxItems=100。执行层 bind_pdf_request 又将页数绑定为 1，在 pdf_render_tool.py:68 才拒绝。

模型传 3 项、2 项并加入 `_END_` 是模型参数/协议错误，不能全归工程。但平台把约束放在较晚阶段，增加了可避免的昂贵返工。应对所有 render_pdf 工具应用同一用户契约，与是否需要搜索解耦。不能通过无条件拼接所有 pages 来掩盖真正多页内容，更不能保留 `_END_` 当正文。

### E3：止损器把不同阶段错误混算成同类

tool_failure_recovery.py:24–31 只看工具名及大类错误码，render_pdf 的所有 pdf_render_failed 都被累计；没有将 data.stage、错误原因或内容版本纳入失败签名。

本轮两次 pages 参数错误 + 一次未知符号错误触发 attempts=3。第三次错误刚出现，agent_loop.py:566–571 就 break，模型没机会看到这条新错误后修复。只读复现将真实全部收据传入函数，返回 attempts=3；只传第三次符号错误则不触发停止。

止损本身应保留，但应同时设置总预算与按故障类别的预算，识别“输入已修复、进入新阶段”的真实进展。不要简单把限制从 3 提到更大的固定数。

### E4：所有尝试都失败时，PDF 专属终态没有接管

末尾 PDF 分支只在 managed_pdf 或 has_registered_renders() 为真时运行。联网路径 managed_pdf=false；三次都失败，没有注册有效 render。即使 pdf_render_tool 已记录具体 _LAST_FAILURE，末尾也不会取 pdf_delivery_result，而是进入通用 finalizer、retrieval_answer 和 deliverable_contract。

因此最终只剩“错误累计达到上限”及 missing_physical_file_.pdf，真实原因被遮蔽。应按“本轮尝试过 PDF 生成”接管失败终态，不以“已经成功注册候选”作为失败呈现的前提，并向用户说明具体工程错误。

“未落盘”对本轮新的合格交付版本是准确的；不代表工作区没有任何旧 PDF。没有 OS 文件权限、磁盘空间或路径挂载故障的证据。“补充条件”是通用模板措辞，不符合本轮实际情况。

## 6. 内容与模型问题

除了 `_END_` 和多项 pages，第三稿还有来源不支持的内容：两次检索热搜第 8 是“伊莫S1赛季PV”，稿中替换为“小米SU7 Ultra纽北圈速刷新纪录”；又把“伊莫S1赛季PV发布”写成 180 万播放，而本轮收据只在热搜中出现该主题，没有对应视频播放量。

这属于基于本轮证据的内容漂移/无依据数值，不能作为真实榜单交付。此次没有进入视觉验收，也不能证明去掉图标后就会通过内容验收或保持一页。后续验证必须包含来源逐条核对、页数和完整 PNG，而非只让生成器退出码变成 0。

## 7. 哪些防线生效、哪些验证缺失

生效：受控 PDF 工具取代临时 bash 排版；参数检查拦截不符合一页契约的数组；未知字形没有变成坏文件交付；止损停止继续耗时；本轮 verified=false，未声称已成功。

缺失：未知装饰图标的可用降级、联网路径 schema 绑定、按失败原因的修复预算、PDF 首次渲染前失败的专属终态，以及真实模型生成新稿的端到端成功验证。

此前“56 项检查通过”仅说明当时的有限样例和门禁测试通过。它没有覆盖本次这组模型参数、常见未知图符、页数错误后切换到符号错误、全部原生渲染失败但无注册 render 的组合。因此上轮“已修复”不能理解为整个真实生成链路已验证完成。

## 8. 修复与验收优先级

1. 将未知装饰图符转换为安全替代，保留数据语义；用多主题、多组图符验证，不写 Bilibili 专用名单。
2. 对所有 render_pdf schema 绑定用户页数要求；规范处理模型协议哨兵，不删除真实内容。
3. 将失败签名细化到输入契约、内容、符号、真实分页、字体、视觉、传输等原因，保留任务总预算。
4. 只要本轮尝试 PDF，就以专属失败状态输出具体原因；不让通用“补充条件/未落盘”覆盖诊断。
5. 保存本次参数为回归夹具，补上真实生成→结构检查→来源核对→逐页视觉→哈希一致发布的闭环，再复测一次用户原始请求。持续保留拒绝坏文件的门禁。
6. 单独处理 60 秒上游空闲与重试观测，压缩明确单页任务的 41 秒前置决策/规划成本；不要把模型延迟误算成 PDF 渲染慢。
