# 澄清与结果验收分离

模型有权在上下文不足、必要字段或业务定义缺失时询问用户。评测不要求一次回复必然得出数值，不把合理澄清计为模型失败。

## 可接受的交互结果

- `valid_clarification`：说明具体缺口，提出能够消除歧义的问题，等待用户答复。
- `valid_partial_clarification`：给出已经有来源支持的部分结果，说明剩余缺口并询问；不把局部完成称为全部完成。
- `grounded_data_gap`：如实说明必要信息不在当前可用数据中，并指明需要补充的数据或定义。
- `answer_with_stated_assumption`：低风险只读任务中，明确说明所用合理口径后提供可核验结果；澄清是权利，不是强制问句要求。
- `engineering_blocked`：如实说明读取、工具或系统异常，必要时请用户重传或提供替代来源。交互可以合理，执行仍记录为工程阻断，不归罪于模型。

合理澄清的**本轮交互通过**，整个计算任务记录为 `awaiting_user`；不要求其具备计算结果的 verified=true。用户补充后，应继续验证相同会话是否使用新口径完成任务。

## 证据与边界

1. 审核用户原文、模型实际可见的上下文、已执行工具、错误与最终回复；不能只因评测端知道答案，就认定模型不应澄清。
2. 问题应明确指向缺失的字段、期间、维度、单位、范围或定义；只说“请补充情报”而无上下文依据，先记待复核，不自动判模型错误。
3. 技术异常与业务信息缺失分开归因。模型可以解释异常并请求可行补充，但不能把工具接口错误伪称为用户业务数据缺失。
4. 澄清可引用有来源的数值、用户给定阈值或口径备选项；不能借“请确认”把未核验的计算结果写成既定事实。
5. 关键词或产品的 clarification guard 只能提供候选信号，不能自行证明澄清合理。人工/独立评审结论绑定 session ID 与最终回复 SHA-256，避免重跑后沿用旧判定。
6. 主结果数值状态、交互质量、任务完成状态分别记录。未计算不等于算错；合理澄清不等于计算已完成；HTTP done 或 verified=true 也不等于完整回答正确。

固定查询基线仍可用于精确差分，但应允许有依据的澄清作为合法分支。缺口、工具异常、错误断言和模型行为需要分别报告。
