非常好，你这个需求本质是：

> **每个员工用自己的企业身份登录（SSO），在“打开浏览器会话”时可以选择/载入该员工的浏览器配置（Profile），而这些 Profile 的创建、版本、授权、审计都由控制面统一管理。**

这正是把“浏览器当作受控工作负载（workload）”来治理，而不是把权限散落在 noVNC/容器里。下面我给你一个**可直接落地**的架构设计（含数据模型、流程、接口、与 `johnymoo/chrome-novnc-docker` 的结合点）。

> 说明：`johnymoo/chrome-novnc-docker` 的核心能力是提供一个可视化接管的 noVNC 通道和一个可自动化连接的 CDP 端口（并且按 README 明确暴露了 8080/noVNC、5900/VNC、9222/CDP 这类端口契约）。 [\[bing.com\]](https://bing.com/search?q=rrweb+session+replay+open+source+GitHub)

## 1) 你说的“配置”应该定义成什么？（Profile 的边界）

建议把“浏览器配置”拆成 **三层可组合的 Profile**，这样既能满足“员工个性化”，又能满足“企业合规的统一控制”：

### A. Employee Profile（员工个人态）

*   Cookies / LocalStorage / IndexedDB（登录态、站点偏好）
*   浏览历史、自动填充（通常建议禁用或受控）
*   **可选：持久化下载目录**（强建议受控隔离）

### B. Enterprise Baseline（企业基线）

*   Chrome Policy（禁下载、禁密码保存、强制代理、证书信任、禁扩展安装等）
*   预装扩展（如企业证书、DLP、SOCKS/Proxy helper）
*   默认主页/书签/白名单等

### C. Task/Template Overlay（任务叠加层）

*   仅对某些模板任务生效的临时设置（例如允许访问某个额外域名 30 分钟）
*   与审批/风控绑定（高风险操作必须审批）

> 组合方式：**Session = Enterprise Baseline + (Employee Profile 可选) + (Task Overlay 可选)**  
> 这样才能把“员工可选载入”做成一个严格受控的选项，而不是随意挂载整个用户目录。

## 2) 控制面如何管理 Profile：数据模型与权限

### 2.1 Profile 在控制面中的“对象模型”

建议在控制面维护一个 Profile Registry（配置仓库）：

*   `profile_id`
*   `owner_user_id`（员工唯一身份，来自 SSO）
*   `type`：`employee | baseline | overlay`
*   `version`：语义化版本/时间戳
*   `storage_ref`：对象存储路径（加密压缩包）或镜像层引用
*   `policy_tags`：比如 `DLP=on`, `download=off`, `proxy=corp`
*   `allowed_templates`：哪些模板可以使用此 profile（可选）
*   `last_used_at / last_modified_at`
*   `audit_trail`：谁创建/更新/使用/导出

### 2.2 Profile 的授权规则（必须在控制面）

**最重要的规则**：

*   员工只能选择自己的 `employee profile`
*   企业管理员才能发布 `baseline profile`
*   `overlay profile` 必须和审批/风控绑定（例如“临时放开某域名”）

这能保证即使 noVNC/CDP 端口存在，真正的“载入谁的浏览器态”仍由控制面裁决，而不是靠容器内文件权限。

## 3) 运行时怎么把 Profile 注入到 `chrome-novnc-docker` 会话里？

你要的是“加载浏览器时作为选项载入配置”，最稳妥的实现方式是：

> **控制面负责“选择与授权”，会话经纪人（Session Broker）负责“把选中的 profile 以可控方式注入浏览器容器”，并在会话结束时决定是否持久化回写。**

结合 `chrome-novnc-docker` 这类 worker 的典型做法：容器里 Chrome 会使用一个 `--user-data-dir`（例如 `/data/chrome`）作为 profile 存放目录。 [\[bing.com\]](https://bing.com/search?q=rrweb+session+replay+open+source+GitHub)

### 推荐三种注入策略（按企业常用程度排序）

#### ✅ 策略 1：对象存储 Profile 包（推荐）

*   控制面把 profile 打包加密存对象存储（S3/MinIO/Azure Blob）
*   Session Broker 创建会话时签发 **一次性下载 URL/短期凭证**
*   Browser Worker 启动时：
    1.  下载 profile 包到临时目录
    2.  解密解压到 `/data/chrome`
    3.  启动 Chrome 指向该目录
*   会话结束时：
    *   若策略允许持久化：重新打包→上传→版本+1
    *   若不允许：直接销毁（只读会话）

**优点**：不依赖宿主机共享盘；易于多节点扩展；审计与版本天然可做。  
**注意**：要配合“控制锁”避免并发写同一 profile（下文会讲）。

#### ✅ 策略 2：网络文件系统/卷挂载（适合单集群）

*   每个员工一个 PVC/NFS 路径：`/profiles/{user_id}`
*   Worker 创建时把该卷挂载为 `/data/chrome`
*   Chrome 直接在这个目录读写

**优点**：性能好、实现简单  
**缺点**：对多集群/跨区域不友好；隔离与备份要做好

#### ⚠️ 策略 3：镜像层（只适合 baseline）

*   企业 baseline profile 做成 Docker layer（只读）
*   员工 profile 仍用策略 1/2
*   session overlay 通过 init script 修改少量配置

**适用**：企业基线很稳定，需要极快启动

## 4) 控制面“选择载入配置”的完整流程（从 UI 到容器启动）

下面是一个你可以直接画进评审 PPT 的流程：

### 4.1 创建会话（用户选择 profile）

1.  员工登录 Portal（SSO）
2.  点击“新建浏览器会话”
3.  在选项中选择：
    *   `use_employee_profile = true/false`
    *   可选：选择一个 `task overlay`（若有权限）
4.  Portal 调用 Control Plane：`POST /sessions`

### 4.2 控制面裁决（AuthZ + 风控 + 锁）

Control Plane 做：

*   校验用户对该 profile 有无权限
*   校验模板/任务是否允许加载该 profile
*   **拿 profile 写锁**（如果该会话允许写回）
*   生成会话租约（lease）与短期令牌：
    *   `novnc_token`（接管时才发或先发只读）
    *   `cdp_token`（给回放引擎连接 CDP）
    *   `profile_fetch_token`（给 worker 拉 profile）

### 4.3 Worker 启动并注入

Session Broker 调度 Worker（即你的 `chrome-novnc-docker` 派生镜像）并传入：

*   `PROFILE_FETCH_URL` 或 `PROFILE_BLOB_KEY`
*   `PROFILE_DECRYPT_KEY_REF`（引用 KeyVault，不直接传明文）
*   `USER_DATA_DIR=/data/chrome`
*   `MODE=readwrite/readonly`

Worker 初始化完成后：

*   通过 noVNC（8080）提供画面接管
*   通过 CDP（9222）提供自动化入口（注意应当经网关/代理，不建议裸露） [\[bing.com\]](https://bing.com/search?q=rrweb+session+replay+open+source+GitHub)

### 4.4 会话结束（是否写回）

*   若该会话允许写回员工 profile：
    *   Worker 打包并上传新版本
    *   Control Plane 释放 profile 锁
    *   审计记录“谁在何时更新了哪个 profile”

## 5) 并发与一致性：为什么必须要“Profile Lock”

你会很快遇到一个现实问题：

> 同一个员工可能同时开两个会话（或 AI 在跑 + 人又开了一个调试会话），如果都写回同一个 profile，cookie/登录态会被互相覆盖。

**解决方案（推荐）**：

### 方案 A：写锁（最简单）

*   一个 `employee profile` 同时只能有一个 `read-write session`
*   其他会话只能 `read-only` 或基于快照 `clone`

### 方案 B：Copy-on-Write（更灵活）

*   选择 profile 时先**克隆一个 session-local copy**
*   会话结束时由控制面决策：
    *   合并回主 profile（需要冲突策略）
    *   或仅保留为一个新版本（manual promote）

对于企业合规场景，**写锁 + 只读会话**通常足够，且审计清晰。

## 6) 你要求“配置在控制面管理”——建议的 API 设计（最小集合）

下面这些接口一旦定好，你的“选项载入配置”就能工程化：

### Profile Registry

*   `GET /profiles?owner=me`：列出员工可用 profile
*   `POST /profiles`：创建/导入 profile（管理员/员工）
*   `POST /profiles/{id}/publish`：发布 baseline（管理员）
*   `POST /profiles/{id}/snapshot`：生成快照版本
*   `POST /profiles/{id}/revoke`：禁用（合规需要）

### Session Lifecycle

*   `POST /sessions`：创建会话（参数：template\_id、use\_profile、overlay\_id…）
*   `POST /sessions/{id}/attach-novnc`：签发/升级 noVNC token（只读→可控）
*   `POST /sessions/{id}/attach-cdp`：签发 CDP token（给 Replay Engine）
*   `POST /sessions/{id}/takeover`：进入 HUMAN\_CONTROL（冻结引擎输入）
*   `POST /sessions/{id}/resume`：恢复引擎
*   `POST /sessions/{id}/close`：结束会话（触发写回/释放锁）

## 7) 与模板回放引擎的耦合点（为什么你必须把引擎外置）

你前面已经对齐过：回放引擎要外置，通过 CDP 控制同一个会话。这里再补一条和“员工 profile”强相关的原因：

> **回放引擎必须知道会话当前 loaded profile 是谁**，以便做审计与幂等（例如“这个动作是以 user\_id=xxx 的登录态完成的”）。

因此 Session Broker 需要把 `session_id ↔ profile_version ↔ user_id` 固化在审计里，这样你才能把“谁的权限在什么时候驱动了哪些浏览器动作”讲清楚。

同时，Playwright 的 Trace/Trace Viewer 能记录操作步骤、定位器、网络等，非常适合用作证据链的一部分（尤其在涉及“员工权限操作”的合规场景）。 [\[docker.aityp.com\]](https://docker.aityp.com/image/docker.io/dorowu/ubuntu-desktop-lxde-vnc:latest), [\[dev.to\]](https://dev.to/yang_ella_f2a3e16ccb54550/shou-gou-liao-wang-luo-fan-pa-zhe-tao-webtop-fang-an-rang-yun-duan-openclaw-xiang-zhen-ren-yang-shang-wang-1npb)

## 8) 最推荐的“选项载入配置”用户体验（Portal 交互建议）

员工点“新建会话”时的最小 UI：

*   ✅ 勾选：**加载我的浏览器环境（推荐）**
*   下拉：**环境版本**
    *   `latest`
    *   `v2026.03.31`
    *   `只读快照（用于安全调试）`
*   可选：**启动模板**
*   可选：**申请临时 overlay**（需要审批）
*   明示：该会话是 `read-only` 还是 `read-write`

这样用户直观、审计也清楚。
