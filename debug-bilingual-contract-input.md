# Debug Session: bilingual-contract-input

Status: OPEN
Date: 2026-05-28

## User Goal
- Run end-to-end validation directly, without adding test cases.
- Verify bilingual document input handling:
  1. For bilingual fields like acceptance deadline in Chinese/Japanese, only one semantic parameter should be recognized, and the Japanese value should be auto-generated by translation.
  2. When asking the user for missing inputs, bilingual cases should not display duplicated parameters with the same semantic meaning.

## Initial Hypotheses
1. Missing-input extraction is keyed by localized display labels instead of canonical semantic keys, so Chinese/Japanese variants are treated as separate required fields.
2. The bilingual parameter-normalization step exists for template rendering but is skipped in the "wait for user input" stage.
3. Translation backfill only happens after user input is complete, so the collector still requests both zh/ja fields before translation can run.
4. The prompt builder or task executor expands bilingual metadata into two visible prompts even if upstream semantic deduplication already happened.
5. The issue is specific to the "创建技术服务合同" template workflow configuration rather than the generic template workflow engine.

## Constraints
- No business logic changes before runtime evidence is gathered.
- First code change must be instrumentation only if instrumentation is needed.
- No test case additions for this task.

## Runtime Evidence
1. `TemporalWorkflowService.buildTemplateWorkflowParamSeeds()` reproduced duplicated required inputs when skill parameters exposed `acceptanceDays_zh` and `acceptanceDays_ja`. Before the fix, the runtime output contained two independent seeds:
   - `acceptanceDays_zh`
   - `acceptanceDays_ja`
2. `ChatController.formatWaitingInputMessage()` reproduced duplicated waiting-input text. Before the fix, the runtime output was:
   - `缺少参数：验收期限天数（中文）、验收期限天数（日文）、委托方名称（中文）、委托方名称（日文）`
3. `TemplateWorkflowService.renderData()` already proved the downstream bilingual generation behavior was correct once a canonical semantic field was used:
   - input: `委托方是广州日产通商贸易有限公司，验收期限为30天`
   - output included `acceptanceDays_zh`, `acceptanceDays_ja`, `partyAName_zh`, `partyAName_ja`

## Conclusion
- Hypothesis 1 confirmed: upstream template-workflow parameter generation used localized variable keys instead of canonical semantic field IDs.
- Hypothesis 2 confirmed: the waiting-input stage inherited duplicated zh/ja params and displayed them directly.
- Hypothesis 3 partially confirmed: downstream render already auto-generated bilingual values, but upstream input collection still requested both variants.
- Hypothesis 4 confirmed as a presentation-layer symptom: chat waiting-input formatting showed the duplicated bilingual params as-is.
- Hypothesis 5 rejected: the problem is generic to template workflow generation + waiting-input rendering, not unique to a single template.

## Fix Applied
1. In `apps/backend/core/platform/src/modules/temporal-workflow/temporal-workflow.service.ts`
   - Canonicalize template workflow input params by `renderPlan.binding.fieldId` when multiple bilingual variable paths map to the same semantic field.
   - Normalize display labels/descriptions by removing trailing language markers like `（中文）`, `（日文）`, `_zh`, `_ja`, `_cn`, `_jp`.
2. In `apps/backend/core/ai-orchestrator/src/controllers/chat.controller.ts`
   - Deduplicate user-visible waiting-input labels by semantic label.
   - Apply the same dedupe to follow-up hints and waiting-input submission feedback.

## Post-Fix Verification
1. `buildTemplateWorkflowParamSeeds()` now returns:
   - `acceptanceDays`
   - `partyAName`
2. `formatWaitingInputMessage()` now returns:
   - `缺少参数：验收期限天数、委托方名称`
3. `renderData()` still returns bilingual output from a single semantic input:
   - `acceptanceDays_zh: "30"`
   - `acceptanceDays_ja: "30"`
   - `partyAName_zh: "广州日产通商贸易有限公司"`
   - `partyAName_ja: "広州日産通商貿易有限公司"`
